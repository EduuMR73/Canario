# Modelo de amenazas

Canario: canal de denuncias anónimo multi-empresa. Backend API REST (FastAPI, PostgreSQL).

Estado del documento: borrador 11. Las decisiones técnicas de infraestructura y de base de datos se han contrastado con documentación (sección 11), y la frontera con el exterior (proxy y API), la conexión de la API a la base de datos, el cifrado con sus claves, la denuncia anónima con su seguimiento, la supresión legal, la identidad del personal, la instrucción de las denuncias, la redacción de datos dentro de una denuncia, la inyección SQL con la validación de la frontera y la cadena de suministro además con pruebas reales (`tests/security/verificar_esquema.py`, `tests/security/verificar_esqueleto.py`, `tests/security/verificar_arranque.py`, `tests/security/verificar_denuncia.py`, `tests/security/verificar_personal.py`, `tests/security/verificar_inyeccion.py` y `tests/security/verificar_escaneos.py`), y la lógica pura de `app/` con pruebas unitarias y mutantes (`tests/unit/`, ejecutadas por `tests/security/verificar_unitarios.py`). No queda ninguna decisión pendiente de verificar: lo no implementado se marca como "diseñado, no implementado" y los límites están en la sección 8.

## 1. Objetivo y alcance

El sistema permite que una persona denuncie de forma anónima irregularidades en una organización y mantenga una conversación con quien instruye el caso, sin que su identidad quede registrada en ningún punto del sistema.

Dentro del alcance: la API, la base de datos, el proxy inverso y Redis. El almacenamiento de adjuntos (6.6) y los avisos al personal (6.5) están diseñados, no implementados (10): este documento los describe para que su diseño quede fijado, y cada sección lo marca.

Fuera del alcance: el frontend, el cliente del denunciante, la red del usuario y el sistema operativo del servidor anfitrión.

## 2. Actores

| Actor | Descripción | Nivel de confianza |
|---|---|---|
| Denunciante anónimo | Solo posee un código de seguimiento | Ninguno, solo su código |
| Atacante externo | Sin cuenta ni código | Nulo |
| Instructor | Personal que instruye las denuncias que tiene asignadas (6.15) | Parcial, limitado a su empresa y a sus denuncias asignadas |
| Admin de empresa | Gestiona las cuentas del personal y asigna las denuncias de su empresa; lee el contenido solo de las que tiene asignadas (6.15) | Parcial, limitado a su empresa; sin acceso al contenido por ser admin |
| Operador de la plataforma | Da de alta empresas, claves y el primer admin, y recupera un admin (6.12) | Su rol de base de datos no puede leer denuncias; quien opera el anfitrión tiene todos los secretos (8) |
| Empresa hostil | Un tenant que intenta acceder a datos de otro | Nulo fuera de su empresa |
| Empresa denunciada | Intenta identificar al denunciante | Nulo |
| Acceso a BD o backups | Persona con volcado o copia de la base de datos | Nulo sobre el contenido mientras no tenga también la clave maestra (6.4): por eso su copia se guarda separada de las de la base de datos (README) |

## 3. Activos, por criticidad

1. Identidad del denunciante (incluye cualquier dato que permita inferirla).
2. Contenido de denuncias y mensajes. Los adjuntos, cuando se implementen (6.6), tendrán la misma criticidad.
3. Claves de cifrado (clave maestra y claves por empresa).
4. Credenciales del personal y secretos TOTP.
5. Log de auditoría.

## 4. Fronteras de confianza

```
Internet -> proxy (Caddy) -> API (FastAPI) -> PostgreSQL
                                           -> Redis (sin persistencia)
                                           -> SMTP (avisos al personal)          [diseñado, no implementado]
                                           -> Volumen de adjuntos (cifrado)      [diseñado, no implementado]
```

Cada flecha es una frontera: lo que cruza se valida, se limita y se registra sin datos identificativos. Las dos marcadas no existen todavía: hoy la API no envía correo ni guarda ficheros.

## 5. Principios de diseño

- **Defensa en profundidad:** el aislamiento entre empresas se aplica en la aplicación y de nuevo en la base de datos (Row Level Security).
- **Falla cerrado (fail securely):** ante un error en un control de seguridad se deniega, nunca se permite. Sin contexto de empresa, las consultas devuelven cero filas. Sin limitador, se rechaza.
- **Mínimo privilegio:** la API nunca conecta como superusuario ni como dueño del esquema.
- **Explícito sobre implícito:** los permisos se conceden uno a uno, no se heredan por defecto.
- **Lo que no se guarda no se puede filtrar:** no se almacenan IPs ni horas exactas.
- **Los fallos son visibles:** los errores de seguridad se registran (sin datos personales) y no se silencian.

## 6. Decisiones de diseño relevantes

### 6.1 Anonimato real

El denunciante no tiene cuenta. La única credencial es un código aleatorio de 160 bits generado con `secrets`. Solo se guarda su HMAC, calculado con una clave del servidor. Si se pierde el código no hay recuperación: es el precio del anonimato.

- **Formato:** 160 bits son 32 caracteres exactos en base32 (RFC 4648), sin relleno ni bits sobrantes, que se muestran en 8 grupos de 4 separados por guiones. Con 128 bits saldrían 26 caracteres con 2 bits sobrantes, y habría que rechazar a mano las formas no canónicas. Al leerlo se admiten minúsculas, guiones y espacios; todo lo demás se rechaza sin distinguir el motivo. Se comprueba que el texto es ASCII antes de pasarlo a mayúsculas: si no, un carácter como la ligadura "ﬀ" se convertiría en dos letras válidas.
- **HMAC:** HMAC-SHA256 con la clave `clave_hmac_codigos`, de uso exclusivo, y una etiqueta de dominio (`canario/seguimiento/v1`) delante del código. No hace falta un hash lento como el de una contraseña: con 160 bits de entropía la fuerza bruta es inviable. La clave del servidor impide además comprobar códigos con un volcado de la base de datos y sin ella. GlobaLeaks hace lo contrario: un recibo de 16 dígitos (unos 53 bits), compensado con Argon2 y prueba de trabajo.
- Implementado en `app/cripto.py`; lo usan `app/denuncias.py` y `app/rutas_denuncias.py`.
- **Alta:** `POST /v1/empresas/{identificador}/denuncias` devuelve 201 con el código y la fecha, y nada más (nunca el id interno de la denuncia). El código se muestra una sola vez. La denuncia y el HMAC de su código se guardan en la misma transacción: o los dos o ninguno.
- **Seguimiento:** `POST /v1/seguimiento` con el código en el cuerpo, nunca en la URL, para que no quede en historiales, en la cabecera `Referer` ni en ningún registro de rutas. Devuelve el estado, la fecha, la categoría, el texto y los mensajes. Lee en una transacción de solo lectura con `REPEATABLE READ`: la denuncia y sus mensajes salen de la misma foto de los datos, no de dos momentos distintos.
- **Mensajes:** `POST /v1/seguimiento/mensajes` con el código y el texto en el cuerpo; devuelve 201 con la secuencia y la fecha, y nada más. En el seguimiento, cada mensaje lleva solo secuencia, fecha, autor y texto. El autor es `denunciante` o `personal`, nunca quién del personal (`autor_id`), y ningún id interno sale de la API (6.13).
- **Respuestas uniformes:** una empresa desconocida, mal formada o inactiva da exactamente el mismo 404 que cualquier ruta inexistente, así que no se puede distinguir "esa empresa no existe" de "esa URL no existe". Un código mal formado o inexistente da siempre el mismo 404 del seguimiento, también al enviar un mensaje.
- **Sin sesión:** el código viaja en cada petición, por TLS y sin quedar en ningún log, y la API no guarda estado. GlobaLeaks abre una sesión tras el recibo; aquí queda como alternativa, porque exige estado en el servidor.

El anonimato no depende solo de la aplicación. También exige que el proxy no registre IPs, que Redis no persista nada y que los contadores de rate limit usen IP hasheada con una sal que rota y vive solo en memoria (ver 6.8).

### 6.2 Aislamiento entre empresas

- `ENABLE` y `FORCE ROW LEVEL SECURITY` en todas las tablas con datos de empresa. Sin `FORCE`, el dueño de la tabla se salta las políticas; superusuarios y roles con `BYPASSRLS` las saltan siempre. Sin política, el acceso se deniega.
- La política compara `company_id` con una variable de sesión fijada con `set_config(..., true)` dentro de cada transacción, con parámetro enlazado (nunca concatenado). Tras la transacción, `current_setting(..., true)` devuelve cadena vacía y no NULL, por eso la política usa `nullif(..., '')`. Es imprescindible con pool de conexiones.
- Roles de base de datos separados: `migrador` (dueño del esquema), `aplicacion` (API, sin `BYPASSRLS`, sin `TRUNCATE` ni `REFERENCES`), `plataforma` (alta de empresas y supresión, sin acceso a denuncias). Sin login, los dueños de las funciones de definidor: `propietario_funciones` (las de la API y del alta), `propietario_supresion` (la única que borra, 6.14) y `propietario_redaccion` (las únicas que reescriben contenido cifrado, 6.18).
- Las comprobaciones de unicidad y de claves foráneas se saltan RLS. Para que un error de duplicado no revele datos de otra empresa, las restricciones `UNIQUE` incluyen `company_id` y las claves foráneas son compuestas (`company_id`, `id`).
- Tablas de búsqueda sin RLS y sin permisos directos para la API: `tracking_lookup` (HMAC del código, `report_id`, `company_id`) y `company_directory` (`public_id`, `company_id`). Solo se leen a través de funciones.
- Funciones `SECURITY DEFINER` (`resolve_company`, búsqueda de código): `search_path` fijado sin esquemas escribibles y con `pg_temp` al final; `REVOKE EXECUTE ... FROM PUBLIC` explícito y `GRANT EXECUTE` solo al rol que corresponda. Las funciones pertenecen a un rol propio sin `BYPASSRLS`.

### 6.3 Identidad del personal

Implementado en `app/personal.py` (lógica, sin HTTP) y `app/rutas_personal.py` (transporte). El identificador público de la empresa no es un secreto, solo un identificador.

- **Alta por invitación:** una cuenta nace sin credenciales. Su titular, con un token de invitación de un solo uso (72 horas), elige su contraseña y recibe un secreto TOTP; la cuenta solo se activa cuando confirma un código, y entonces recibe su primer dispositivo de confianza. La contraseña y el secreto pendientes esperan en la invitación: una reinvitación no deja la cuenta a medias, y la cuenta sigue funcionando con sus credenciales hasta que se confirma (salvo en la recuperación de emergencia, que revoca en el acto). Nadie más que el titular conoce sus factores.
- **Primer admin:** `gestion alta-admin` (6.12) emite la invitación solo si la empresa no tiene ningún admin activado, y deja una fila en la auditoría de la empresa con actor `plataforma`: la empresa ve cualquier invitación emitida desde la plataforma. Después, las cuentas las gestionan sus admins por la API. Límite: quien opera `gestion` ya tiene todos los secretos (8); esto no le impide abusar, lo hace visible.
- **Recuperación** (NIST SP 800-63B-4, 4.2; Microsoft Entra, cuentas de acceso de emergencia). Canario es personal gestionado por su empresa, como un directorio corporativo, así que la recuperación la hacen otras personas y nunca el titular solo:
  - **Contactos de recuperación:** los admins de la empresa. Un admin reinvita la cuenta por la API; la cuenta sigue funcionando hasta que su titular confirme la invitación, y al confirmar se revocan sus sesiones y dispositivos anteriores.
  - **Sin códigos de recuperación guardados:** recuperarían un factor sin que nadie de la empresa se enterase, y un código guardado es un secreto más que se puede perder o robar. En un canal de denuncias, la empresa debe saber quién recupera el acceso del personal que lee las denuncias.
  - **Aviso (NIST SP 800-63B-4, 4.2.3, "account recovery SHALL cause a notification"):** sin correo, el aviso está dentro de la API. Toda invitación abierta aparece como `invitacion_pendiente` en `/yo` (para el titular) y en la lista de cuentas (para los admins), y cada reinvitación deja su fila de auditoría. Quien recibe una reinvitación que no pidió sigue entrando hasta que alguien la confirme, y un admin puede anularla (`DELETE .../{usuario_id}/invitacion`, auditado como `anulacion_invitacion`).
  - **Recuperación de emergencia:** si el único admin pierde sus dispositivos o su TOTP, nadie de su empresa puede reinvitarlo: la API exige un admin y `alta-admin` se niega si ya hay uno activado. `gestion reinvitar-admin` (6.12) es el último recurso. Solo actúa sobre un admin que ya estuvo activado en esa empresa (un admin pendiente es el caso de `alta-admin`; un instructor lo recupera su admin), así que las dos órdenes no se solapan. **Revoca en el acto**: desactiva la cuenta, revoca sus sesiones y dispositivos y emite la invitación. El motivo: esta orden solo se usa cuando el titular ya no puede autenticarse, así que lo que siga autenticado en esa cuenta no es él; si siguiera dentro, podría anular la invitación y la recuperación no llegaría nunca. Al titular no le cuesta nada, porque no podía entrar. Se salta a propósito la regla que impide quedarse sin admins: la cuenta queda pendiente de su titular, no perdida. Deja la fila `reinvitacion_admin_plataforma` (actor `plataforma`).
  - **Procedimiento fuera de banda** (lo fija este documento, el código no puede imponerlo): antes de ejecutar `reinvitar-admin`, quien opera la plataforma verifica la petición con el contacto de la empresa que consta en el contrato, nunca con el teléfono o el correo que da quien la pide; entrega el token por un canal distinto del de la petición; y avisa a ese contacto de que se ha hecho, que es el aviso "a su designado" de NIST. Si la recuperación no la pidió el admin real, lo nota en el acto (se queda sin acceso), y la auditoría muestra quién y cuándo.
  - **Dos admins por empresa, como mínimo:** es la recomendación de Microsoft para las cuentas de emergencia ("two or more"). Con dos, uno recupera al otro por la API y la plataforma no interviene. No se impone, porque una empresa pequeña puede tener una sola persona responsable; `alta-admin` lo recomienda al emitir la invitación del primer admin.
- **Contraseña:** Argon2id con m=19 MiB, t=2, p=1 (OWASP Password Storage Cheat Sheet), 18 ms por verificación. El perfil por defecto de `argon2-cffi` usa 64 MiB y la API tiene 256 MiB: un semáforo deja calcular dos hashes a la vez y, si no hay hueco en 2 s, responde 503. Política (NIST SP 800-63B-4, con segundo factor obligatorio): de 12 a 128 caracteres tras normalizar con NFKC, sin contener el email, su parte local ni el nombre de la empresa. Sin lista de contraseñas filtradas (8).
- **TOTP:** RFC 6238 con la biblioteca estándar (SHA-1, 6 dígitos, 30 s, un paso de desfase a cada lado). El secreto, de 160 bits, se cifra con la clave de la empresa y un AAD que lo ata a la cuenta, y guarda su versión de clave. Un código solo vale una vez: se guarda el último paso aceptado (NIST SP 800-63B-4: "accept a given OTP only once while it is valid").
- **Login en una petición:** empresa, email, contraseña y código, más el token de dispositivo si lo hay. No hay un estado "medio autenticado" que defender. Cualquier fallo (empresa inexistente o mal formada, email inexistente, contraseña o código erróneos, cuenta sin activar, dada de baja o bloqueada) da el mismo 401, byte a byte.
- **Tiempos uniformes por construcción:** todos los caminos ejecutan las mismas sentencias (sin empresa, con un contexto aleatorio y cero filas), el mismo Argon2 (contra un hash ficticio si no hay cuenta) y el mismo cálculo de TOTP (con un secreto aleatorio). La reserva del intento confirma con `synchronous_commit` desactivado: sin ello, el commit de una cuenta real esperaba el fsync del WAL y tardaba unos 3 ms más que el de un email inexistente, que no escribe nada (medido: 27,2 frente a 24,1 ms; corregido: 23,9 frente a 24,0 ms).
- **Bloqueo sin denegación de servicio** (OWASP "Slow Down Online Guessing Attacks with Device Cookies", Microsoft Entra Smart Lockout y NIST SP 800-63B-4, 3.2.2). Un bloqueo de la cuenta entera dejaría a cualquiera que conozca un email (el identificador de la empresa es público) bloquear a quien investiga, y la Ley 2/2023 pone plazo a esa investigación (arts. 9.2.c y 9.2.d). Por eso el bloqueo es del camino por el que llega el intento:
  - **Con un dispositivo de confianza** de esa cuenta, los fallos cuentan en el dispositivo: con 5 seguidos espera (1, 2, 4... hasta 60 minutos) y con 20 deja de ser de confianza.
  - **Sin él** (o con uno en espera, retirado, caducado o de otra cuenta), los fallos cuentan en la cuenta, con las mismas esperas; con 100 (el máximo de NIST) este camino se cierra hasta que un admin reinvite al usuario. Sus dispositivos de confianza siguen funcionando.
  - El contador sin confianza solo vuelve a cero con un acierto por ese mismo camino: que el titular entre desde su dispositivo no le regala intentos al atacante.
  - El intento se reserva con un `UPDATE` atómico antes de verificar y se libera al acertar: peticiones simultáneas no consiguen intentos extra. Durante una espera ni siquiera se verifica la contraseña.
  - Un fallo de contraseña y uno de TOTP cuentan igual: quien tenga la contraseña no puede probar códigos gratis.
  - El bloqueo deja un evento en el log (`EVENTO espera_sin_confianza`, `cierre_sin_confianza`, `espera_dispositivo`, `retirada_dispositivo`), con empresa y cuenta y sin IP, y no una fila de auditoría: una inserción más en ese intento lo haría medible.
- **Sesión:** token opaco de 256 bits, revocable (un JWT no lo es), del que solo se guarda su SHA-256 con una etiqueta por tipo de token. Caduca a los 15 minutos sin uso y a las 8 horas en total, y se revoca al cerrarla, al dar de baja la cuenta, al cambiar la contraseña (salvo la actual) y al reactivarla. Una empresa inactiva invalida sus sesiones. Los tokens llevan delante el identificador público de la empresa: la API resuelve la empresa con `resolver_empresa` y busca bajo RLS, sin ninguna función de definidor nueva.
- **Roles:** `admin` gestiona las cuentas de su empresa (invitar, reinvitar, anular una invitación, dar de baja) y asigna las denuncias (6.15); un `instructor` recibe 403. Una cuenta de otra empresa es invisible bajo RLS y da el mismo 404 que una inexistente. La baja del último admin activado se rechaza (409). Ser admin no da acceso al contenido de las denuncias (6.15).
- **Base de datos:** invitaciones, dispositivos y sesiones son tablas con RLS y `FORCE`. La API tiene `INSERT` solo por columna: no puede crear una cuenta ya activada ni elegir una caducidad, que fija la base de datos. Un `CHECK` impone que una cuenta está activada si y solo si tiene contraseña, secreto y versión de clave; un índice parcial, que hay como mucho una invitación abierta por cuenta; y una clave foránea de tres columnas, que el dispositivo de una sesión es de su misma cuenta.
- **Transporte:** el token de sesión en `Authorization: Bearer` y el de dispositivo en el cuerpo del login. Sin cookies no hay CSRF. Un frontend web cambiaría solo `app/rutas_personal.py` (cookies `__Host-` con `HttpOnly`, `Secure` y `SameSite=Strict`, más defensa CSRF con comprobación de `Origin` y token): diseñado, no implementado.

### 6.4 Cifrado

Envelope encryption: clave maestra fuera de la base de datos, clave por empresa envuelta por la maestra. AES-256-GCM con datos asociados (AAD) para impedir mover un texto cifrado de una fila a otra. Campo `version_clave` para permitir rotación. Implementado en `app/cripto.py` con la biblioteca `cryptography` (la estándar de Python no trae cifrado autenticado).

- **Claves del servidor:** `clave_maestra` (solo envuelve claves de empresa) y `clave_hmac_codigos` (solo calcula el HMAC de los códigos, 6.1). Son Docker secrets, nunca variables de entorno: 32 bytes como 64 hexadecimales en minúscula, generados por `scripts/generar_secretos.py`. La API las lee una vez, al arrancar (`app/claves.py`), y no arranca si alguna falta, no tiene ese formato exacto o las dos son iguales (6.10).
- **Clave de cada empresa:** 32 bytes aleatorios por versión. En `clave_empresa` solo está envuelta con la clave maestra. Quien tenga un volcado de la base de datos no tiene ninguna clave.
- **Formato de todo lo cifrado:** versión del formato (1 byte), nonce (12 bytes), cifrado y tag (16 bytes). El byte de formato permite cambiar de algoritmo en el futuro sin ambigüedad sobre cómo leer lo antiguo. Cualquier fallo al descifrar (tag, formato o longitud) es el mismo error, sin detalles.
- **AAD:** el AAD no se cifra, pero se autentica, y ata cada cifrado a su sitio. Es lo que recomienda Google Tink para el cifrado por celda: atar el cifrado a la fila y a la columna. Cada AAD empieza por una etiqueta distinta por tipo y versión, seguida de campos binarios de longitud fija, así que dos AAD distintos nunca coinciden:
  - clave de empresa: etiqueta, `empresa_id` y versión;
  - denuncia: etiqueta, `empresa_id` y `denuncia_id`;
  - mensaje: etiqueta, `empresa_id`, `denuncia_id`, el id del propio mensaje (columna `id` de `mensaje`, con `UNIQUE (empresa_id, denuncia_id, id)`), el autor y `autor_id`. Sin el id del mensaje, un mensaje se podría duplicar en otra fila o intercambiar con otro de la misma denuncia sin que GCM lo notara. Sin el autor, un mensaje del denunciante podría pasar por uno del personal.
- **Qué se cifra de una denuncia:** `{"v": 1, "categoria", "texto"}`. La categoría va cifrada y no en una columna: "acoso" con la fecha, en una empresa pequeña, ya apunta a alguien (GlobaLeaks cifra también los metadatos). En claro solo queda lo que el flujo necesita: estado, fecha (día) y asignación. La categoría es una lista cerrada que valida la API; como va cifrada, se puede cambiar sin migrar la base de datos. Se pierde filtrar por categoría en SQL, y con el volumen de una empresa se filtra en la aplicación. El campo `v` permite cambiar el formato sin ambigüedad.
- **Qué se cifra de un mensaje:** `{"v": 1, "texto"}`, con la versión más alta de la clave de la empresa en el momento de enviarlo. Cada mensaje guarda su `version_clave`: tras una rotación, una misma conversación tiene mensajes de varias versiones y cada uno se descifra con la suya. El id del mensaje lo genera la API, porque forma parte del AAD y hace falta antes de cifrar.
- **Relleno:** antes de cifrar, el contenido se rellena hasta un múltiplo de 256 bytes, con su longitud en una cabecera de 4 bytes. El tamaño del cifrado solo revela el tramo de 256 bytes, no la longitud exacta del texto. Al quitarlo se rechaza cualquier desviación.
- **Nonce:** aleatorio de 96 bits en cada cifrado. NIST SP 800-38D, sección 8.3, exige que con nonces aleatorios una misma clave no cifre más de 2^32 veces. El código no lleva esa cuenta (8, límites asumidos); la rotación da una clave nueva con su propia cuenta.
- **Rotación de la clave de una empresa:** se crea la versión siguiente (6.12). Lo nuevo se cifra con ella y lo antiguo se sigue leyendo con la suya.
- **Rotación de la clave maestra:** diseñada, no implementada. Exige volver a envolver las claves de todas las empresas con la nueva.

### 6.5 Metadatos

- La fecha de la denuncia se guarda redondeada al día; la hora exacta no se almacena.
- **El día es el del calendario de la empresa.** La Ley 2/2023 (art. 9.2.c) cuenta el acuse de recibo desde la recepción, y quien recibe es la organización. Cada empresa tiene su zona horaria (`empresa.zona_horaria`, con un `CHECK` que solo admite las de España: `Europe/Madrid`, `Atlantic/Canary` y `Africa/Ceuta`), obligatoria en el alta. Un trigger calcula la fecha de la denuncia, de cada mensaje y de cada fila de auditoría con `now() AT TIME ZONE` esa zona, y sobrescribe lo que traiga el `INSERT`: ni la API ni una sesión con otra `TimeZone` pueden elegir el día. Con UTC, una denuncia enviada entre las 00:00 y las 02:00 en España quedaría fechada el día anterior; con `Europe/Madrid` para toda la plataforma, una empresa canaria tendría fechas desplazadas entre las 23:00 y las 24:00. El patrón de los sistemas multiempresa (instante en UTC, presentado en la zona de cada empresa) no se puede usar sin guardar el instante; esto es su traducción: el día de la empresa, calculado al recibir.
- Los mensajes se ordenan con un número de secuencia y llevan solo el día, con el mismo cálculo que la denuncia; nunca la hora. El día hace falta para los plazos de la Ley 2/2023 (cuándo llegó la información nueva) y no revela más que la fecha de la denuncia. Las tres tablas calculan el día con su propia copia de la expresión, en vez de una función común: los triggers se ejecutan con los permisos de quien inserta, y una función común exigiría dar `EXECUTE` a cada rol que inserta. Se prefiere el mínimo privilegio a la duplicación, y la desviación entre copias la detecta `verificar_esquema.py`, z (las tres tablas, con una zona de control).
- **Logs del camino anónimo:** una línea de log lleva la hora, y "denuncia creada a las 10:32" desharía la fecha al día. Por eso crear, consultar, enviar un mensaje, un 404, un 409 o un 422 no dejan ninguna línea. Los fallos que sí se registran (empresa sin clave, error de integridad, saturación, error interno) llevan solo el tipo de evento, sin empresa, denuncia ni código. Es la misma regla que GlobaLeaks: "avoid logging sensitive metadata that could lead to the identification of whistleblowers".
- **Avisos al personal** (diseñados, no implementados): se agruparían con un retraso aleatorio y no incluirían contenido. Un aviso inmediato tras cada denuncia, con su hora, desharía la fecha al día, como una línea de log.
- Al denunciante no se le notifica nunca: pedirle un email rompería el anonimato.

### 6.6 Adjuntos

**Diseñado, no implementado** (10). Solo imágenes (re-codificadas, lo que elimina EXIF) y PDF limpiados de metadatos. Se rechazan formatos Office por los metadatos de autor. Validación por magic bytes, tamaño máximo, nombre UUID, cifrado, almacenamiento fuera de cualquier ruta servida y descarga forzada.

### 6.7 Auditoría

La API tiene `INSERT` y `SELECT` (este último bajo RLS) sobre el log, nunca `UPDATE` ni `DELETE`. El hash encadenado lo calcula un trigger en la base de datos, con bloqueo por empresa para evitar carreras.

Las acciones del denunciante **no** se auditan. La auditoría numera los eventos de cada empresa con una secuencia: un "denuncia recibida" entre dos acciones del personal, cuya hora sí se conoce, situaría la denuncia en una franja de minutos y desharía la fecha al día. El libro-registro de la Ley 2/2023 (art. 26) es la propia tabla `denuncia`. Las acciones del personal sí se auditan, con actor `personal:<id de la cuenta>`: acceso, activación, invitación, anulación de una invitación, baja y cambio de contraseña (6.3); sobre las denuncias, cada lectura del contenido (`lectura_denuncia`), cada mensaje (`mensaje_personal`), cada cambio de estado (`estado_<nuevo>`), cada asignación (`asignacion`) (6.15) y cada redacción (`redaccion_denuncia` y `redaccion_mensaje`, esta con el id del mensaje como destino) (6.18); la invitación del primer admin y la recuperación de emergencia de un admin, con actor `plataforma`. Un login fallido no se audita: la cadena no debe poder inundarse con intentos, y el bloqueo va al log de eventos. Los listados tampoco: no muestran contenido.

- **Dos objetos:** la asignación tiene dos, la denuncia (`objeto_id`) y la cuenta que la recibe (`destino_id`). `destino_id` entra en el hash encadenado: sin él, quién recibió una denuncia se podría cambiar sin romper la cadena. Ninguno de los dos lleva clave foránea, para que la auditoría sobreviva a lo que describe (una denuncia suprimida sigue apareciendo por su id).
- **Lectura por la API:** `GET /v1/personal/auditoria`, solo para admins, devuelve las filas de su empresa por orden de secuencia, paginadas con `desde`. `GET /v1/personal/auditoria/verificacion`, también solo para admins, devuelve el resultado de `verificar_cadena_auditoria()` (`cadena_intacta` y `primera_rota`). Van separadas porque verificar recorre la cadena entera (O(n)): en el listado, cada página la recorrería otra vez. Sin estas rutas, los controles que dependen de la auditoría (la autoasignación de 6.15, la reinvitación de 6.3) solo serían visibles para quien opera el anfitrión. Leer o verificar la auditoría no deja fila.

### 6.8 Infraestructura sin rastro de IP

- **Caddy:** no se declara la directiva `log` en ningún sitio, de modo que no hay logs de acceso. Los logs de runtime sí están activos y pueden contener IPs (por ejemplo errores de handshake TLS y errores de upstream). El campo `msg` no se puede filtrar, así que se excluye el logger `http.stdlib` en la opción global `log` y en el resto se borran los campos de IP con el filtro `delete`. No se usan `hash` ni `ip_mask` como anonimización: `hash` conserva solo 4 bytes de SHA-256 y es invertible por fuerza bruta sobre IPv4. Caddy no confía en ningún proxy por defecto y reemplaza el `X-Forwarded-For` entrante.
- **Uvicorn:** `--no-access-log`, sin `--log-config`. Si algún día se usa `--log-config`, el logger `uvicorn.access` debe desactivarse dentro de esa configuración. `--forwarded-allow-ips` se limita a la IP fija del proxy en la red interna `app` (`10.88.0.2`), no a toda la subred; nunca `*`. Sin esto, todos los clientes parecerían la IP del proxy y compartirían un único contador de rate limit.
- **Redis:** `save ""` y `appendonly no`, sin réplicas, red interna y raíz de solo lectura, incluido `/data`: la imagen no declara `VOLUME` (comprobado con `docker image inspect`) y el contenedor no tiene volúmenes ni tmpfs, así que no hay ningún sitio donde escribir un RDB. `SAVE` y `BGSAVE` crean un RDB aunque la persistencia automática esté apagada; además de no poder escribirlo, la ACL los deniega. La ACL desactiva el usuario `default` y deja al usuario `aplicacion` (el mismo nombre que su rol de PostgreSQL: identifica al cliente, la API, con una credencial distinta en cada sistema) solo `PING`, `MULTI`, `EXEC`, `INCR`, `EXPIRE`, `TTL` y `CLIENT SETINFO`, y solo sobre las claves `limite:*`.
- **IP en memoria:** la API usa la IP del cliente solo para derivar la clave de su contador (`app/limitador.py`): HMAC-SHA256 de la dirección con una sal aleatoria de 32 bytes que solo vive en la memoria del proceso, con etiqueta de dominio y truncado a 128 bits. No es un hash con sal pública: sin la sal, un volcado de Redis no permite recorrer las 2^32 direcciones IPv4 para encontrar la de una clave. La sal cambia cada día a las 00:00 UTC y la anterior se descarta; cada ventana divide el día, así que el cambio cae siempre en una frontera de ventana y no parte ningún contador. IPv6 se agrupa por /64 (un cliente con un /64 tendría 2^64 direcciones) y una IPv4 escrita como IPv6 (`::ffff:a.b.c.d`) cuenta como la IPv4. La IP no se escribe en base de datos, logs ni disco; en Redis solo está su HMAC, con TTL.

### 6.9 Comportamiento ante fallos

Si Redis no responde, las rutas con límite (crear denuncia, seguimiento, mensajes, el acceso del personal y cualquier otra salvo `/salud`) devuelven 503 con `Retry-After`. Es la regla única, por el principio de fallar cerrado: no existe ningún camino que se salte el limitador. Consecuencia asumida: durante una caída de Redis, un denunciante debe reintentar. No se expone nada, porque no se almacena nada. Cada rechazo por este motivo genera un evento de seguridad visible, sin IP: `EVENTO limitador_no_disponible: <clase del error>`.

**Limitador** (`app/limitador.py`), implementado:

- **Dónde:** un middleware ASGI asíncrono (`redis.asyncio`), por dentro del de errores internos y por fuera del límite de cuerpo. Rechaza antes de leer el cuerpo y antes de validar, así que cuentan también las peticiones inválidas (422), los cuerpos demasiado grandes (413) y los códigos inexistentes (404): no hay ninguna vía gratuita de sondeo. Al ser asíncrono, un Redis lento no ocupa los hilos de AnyIO de las rutas síncronas.
- **Cerrado por construcción:** toda ruta pasa por el limitador salvo `/salud`, que usa el healthcheck desde dentro del contenedor. Lo que no tiene regla propia cae en la regla `otras`: una ruta nueva queda limitada sin que nadie tenga que acordarse.
- **Reglas por cliente (producción):** crear denuncia, 10 por hora; seguimiento, 60 por minuto; mensajes, 30 por hora; acceso del personal (login, activación y cambio de contraseña), 10 cada 5 minutos; otras, 60 por minuto. Son moderadas a propósito por Tor y NAT (8). En el seguimiento, con 160 bits la enumeración ya es inviable: el límite protege la capacidad.
- **Segunda capa, por cuenta** (OWASP API4:2023, consumo de recursos sin restricción): el límite por IP frena a quien no tiene credenciales, pero no a una cuenta que reparte sus peticiones entre varias IPs o sesiones. Toda ruta con sesión del personal consume además la regla `cuenta` (60 por minuto) con la identidad autenticada. La aplica la dependencia que autentica (`app/rutas_personal.py`), que es la única forma de obtener una sesión: ninguna ruta con sesión queda sin este límite (cerrado por construcción, como `otras`). No puede ir en el middleware, porque ahí todavía no se sabe de quién es la petición. La clave es `limite:cuenta:<ventana>:<hmac>`, con un HMAC de empresa y cuenta, la misma sal del día y su propia etiqueta. Un token que no vale no consume el contador de ninguna cuenta; lo frena la capa por IP. Al superarlo, 429 con `Retry-After`, y el primer exceso de cada ventana deja `EVENTO limite_cuenta` con empresa y cuenta y sin IP: es del personal, no del denunciante, y señala una sesión que se usa de forma anómala. Solo el primero, para que el log no se pueda inundar con 429. Es lo que acota, por cuenta, las filas de auditoría que una sesión puede generar leyendo denuncias.
- **Algoritmo:** ventana fija. `INCR` y `EXPIRE NX` van en un `MULTI`/`EXEC`, que Redis ejecuta entero o no ejecuta, y el número de ventana va dentro de la clave (`limite:<regla>:<ventana>:<hmac>`). Una clave sin TTL no bloquearía a nadie (la ventana siguiente usa otra clave) y `EXPIRE NX` se lo pone con la siguiente petición. No hace falta un script Lua: daría la misma atomicidad y obligaría a abrir `EVAL` en la ACL. Los comandos se envían por su nombre exacto: `Redis.incr()` de redis-py envía `INCRBY`, que la ACL no permite (comprobado).
- **429:** con `Retry-After`, que es el número de segundos hasta el fin de la ventana, y el formato de error de la API. No deja ninguna línea en el log, porque es flujo normal del camino anónimo (6.5). Se pierde visibilidad de los intentos de fuerza bruta: es un coste asumido.
- **Plazos:** 200 ms para conectar y para cada respuesta y un pool de 20 conexiones con 200 ms de espera. redis-py reintenta por defecto varias veces, con espera exponencial; aquí solo se reintenta una vez, de inmediato y solo ante un error de conexión, para sustituir una conexión muerta tras un reinicio de Redis. Un plazo agotado no se reintenta. Comprobado con Redis en pausa: el plazo corta a los 0,2 s.
- **Configuración:** los límites de producción son literales del código. La variable `CANARIO_LIMITES`, opcional y que no es un secreto, los sustituye todos a la vez, incluida `cuenta`. Se analiza de forma estricta: tiene que traer exactamente las mismas reglas, con valores enteros acotados y una ventana que divida el día. Si no es válida, la API no arranca. Los límites efectivos y su origen (`LIMITES (por defecto): ...` o `LIMITES (configurados): ...`) quedan en el log en cada arranque: un límite relajado en producción es visible, nunca silencioso. Hace falta porque las baterías funcionales mandan decenas de peticiones por minuto desde pocas IPs; la del limitador prueba los valores de producción.

Alternativa descartada por ahora: un limitador local en memoria, más estricto, como plan B. Es menos seguro que el 503 (contadores por proceso, se pierden al reiniciar) y añade código poco ejercitado. Queda como "diseñado, no implementado".

Nota de defensa en capas: el bloqueo progresivo del personal vive en PostgreSQL, no en Redis, y se suma al 2FA (6.3). Aunque el limitador no esté disponible o el atacante cambie de IP, adivinar la contraseña de una cuenta concreta sigue frenado. Con Redis parado, un login se rechaza con 503 antes de contar ningún intento.

### 6.10 Secretos y arranque verificado

- Los secretos se pasan como ficheros (Docker secrets), no como variables de entorno. La imagen de PostgreSQL acepta `POSTGRES_PASSWORD_FILE` para el superusuario; las contraseñas del resto de roles se establecen en un script de inicialización que lee los secretos. La API monta exactamente cuatro: la contraseña de `aplicacion`, `clave_maestra`, `clave_hmac_codigos` y `contrasena_redis` (la del usuario `aplicacion` de Redis, que se lee al abrir cada conexión, como la de PostgreSQL). Nunca la de `plataforma`, que solo tiene el servicio `gestion` (6.12).
- Los scripts de inicialización solo se ejecutan con el directorio de datos vacío, y si uno falla y el contenedor se reinicia, el resto se salta sin aviso. Para que ese fallo no sea silencioso, al arrancar la API comprueba la base de datos con el propio rol `aplicacion`, en una transacción de solo lectura, contra valores esperados escritos como literales (`app/verificacion_arranque.py`). Si algo no coincide registra `ARRANQUE BLOQUEADO: <comprobación>` y no arranca; Caddy, que depende de que la API esté sana, tampoco. Son 22 comprobaciones de arranque: 5 previas a abrir el pool (secreto, claves de cifrado, límites, secreto de Redis y conexión), 16 sobre la base de datos y 1 sobre Redis (limitador), al final. 21 de las 22 tienen prueba de desviación: las de claves, límites, secreto de Redis y limitador en `tests/security/verificar_denuncia.py` (c y r) y el resto en `tests/security/verificar_arranque.py`. La comprobación de identidad no tiene prueba de desviación. Cada prueba provoca una desviación representativa (como superusuario en las de base de datos, con una ACL de Redis distinta en la del limitador, con secretos de prueba en las previas), comprueba que el arranque se bloquea y, en las de base de datos y en la del limitador, que al revertirla la API vuelve a arrancar:
  - `search_path` del rol (`pg_catalog, canal`). Qué prueba: que `search_path = canal, pg_catalog` bloquea el arranque y, al revertirlo, la API vuelve a arrancar. Qué no prueba: otros valores, por ejemplo uno que incluya `public`.
  - Identidad (`current_user`, `session_user`, base de datos). La comprobación de identidad no tiene prueba de desviación.
  - Atributos del rol: sin superusuario, `BYPASSRLS`, `CREATEROLE`, `CREATEDB` ni replicación. Qué prueba: que `ALTER ROLE aplicacion BYPASSRLS` bloquea el arranque y, al revertirlo, la API vuelve a arrancar. Qué no prueba: superusuario, `CREATEROLE`, `CREATEDB` ni replicación.
  - Sin pertenencia a ningún otro rol. `pg_read_all_data` no salta la RLS, pero daría lectura de `directorio_empresas` y `busqueda_seguimiento`, que no tienen RLS. Qué prueba: que `GRANT pg_read_all_data TO aplicacion` bloquea el arranque (también como `privilegios_tabla`, por esa lectura) y, al revertirlo, la API vuelve a arrancar. Qué no prueba: la pertenencia a otros roles.
  - Sin propiedad de ningún objeto: el dueño de una tabla puede desactivar su RLS con `ALTER TABLE`, y `FORCE` no lo impide. Qué prueba: que un esquema propiedad de `aplicacion` bloquea el arranque y, al borrarlo, la API vuelve a arrancar. Qué no prueba: la propiedad de tablas, funciones, tipos ni de la base de datos.
  - Sin `CREATE` en `canal` ni `public` y sin `CREATE` ni `TEMPORARY` en la base de datos: las tablas temporales se buscan antes que cualquier esquema del `search_path`. Qué prueba: que `GRANT TEMPORARY ON DATABASE canario` bloquea el arranque y, al revertirlo, la API vuelve a arrancar. Qué no prueba: `CREATE` en `canal`, en `public` ni en la base de datos.
  - Exactamente las 11 relaciones esperadas en `canal`. Qué prueba: que una tabla nueva en `canal` bloquea el arranque y, al borrarla, la API vuelve a arrancar. Qué no prueba: que falte una relación esperada, ni una vista nueva.
  - `ENABLE` y `FORCE ROW LEVEL SECURITY` en las 9 tablas con datos de empresa. Qué prueba: que `NO FORCE ROW LEVEL SECURITY` en `denuncia` bloquea el arranque y, al revertirlo, la API vuelve a arrancar. Qué no prueba: `DISABLE ROW LEVEL SECURITY` ni el resto de tablas.
  - Exactamente los privilegios esperados de tabla. Qué prueba: que `GRANT DELETE ON canal.denuncia` bloquea el arranque y, al revertirlo, la API vuelve a arrancar. Qué no prueba: otros privilegios u otras tablas, ni que falte un privilegio esperado.
  - Exactamente los privilegios esperados por columna. Qué prueba: que `GRANT UPDATE (contenido_cifrado) ON canal.denuncia` bloquea el arranque y, al revertirlo, la API vuelve a arrancar. Qué no prueba: otras columnas, ni que falte un privilegio esperado.
  - `EXECUTE` exactamente sobre las 7 funciones esperadas (nunca `alta_empresa`). Qué prueba: que `GRANT EXECUTE` sobre `alta_empresa` bloquea el arranque y, al revertirlo, la API vuelve a arrancar. Qué no prueba: que falte `EXECUTE` sobre una función esperada.
  - Exactamente las 8 funciones de definidor esperadas, cada una con su dueño: `propietario_funciones` las 4 de la API y del alta, `propietario_supresion` las 2 de la supresión (6.14) y `propietario_redaccion` las 2 de la redacción (6.18). Qué prueba: que `resolver_empresa` con dueño `migrador` bloquea el arranque y, al devolverla a `propietario_funciones`, la API vuelve a arrancar. Qué no prueba: una función de definidor nueva.
  - `propietario_funciones` sin superusuario, `BYPASSRLS` ni login. Qué prueba: que `ALTER ROLE propietario_funciones BYPASSRLS` bloquea el arranque y, al revertirlo, la API vuelve a arrancar. Qué no prueba: superusuario ni login.
  - `propietario_supresion`, el único rol que puede borrar, sin superusuario, `BYPASSRLS` ni login: con cualquiera de ellos, el permiso de borrar dejaría de estar encerrado en su función. Qué prueba: que `ALTER ROLE propietario_supresion BYPASSRLS` bloquea el arranque y, al revertirlo, la API vuelve a arrancar. Qué no prueba: superusuario ni login.
  - `propietario_redaccion`, el único rol que puede reescribir contenido cifrado, sin superusuario, `BYPASSRLS` ni login: con `BYPASSRLS`, sus funciones cruzarían empresas. Qué prueba: que `ALTER ROLE propietario_redaccion BYPASSRLS` bloquea el arranque y, al revertirlo, la API vuelve a arrancar. Qué no prueba: superusuario ni login.
  - Exactamente las 40 políticas esperadas, con su comando, roles, `USING` y `WITH CHECK`. Qué prueba: que una política añadida con `USING (true)` sobre `denuncia` bloquea el arranque y, al borrarla, la API vuelve a arrancar. Qué no prueba: que falte una política esperada o que cambie su condición.
  - Previa: el secreto existe y tiene formato válido. Qué prueba: que un secreto de prueba con salto de línea final bloquea el arranque como `secreto`. Qué no prueba: que la API vuelva a arrancar al corregir el secreto (solo el bloqueo, sin reinicio).
  - Previa: las claves de cifrado (`clave_maestra` y `clave_hmac_codigos`) existen, tienen exactamente 64 hexadecimales en minúscula y son distintas (6.4). Se comprueban antes de conectar, y el motivo del bloqueo nunca lleva su valor. Qué prueba: que sin `clave_maestra`, sin `clave_hmac_codigos`, con la maestra con salto de línea final, en mayúsculas o corta, y con las dos iguales, la API no arranca y registra `ARRANQUE BLOQUEADO: claves: <motivo>`, sin la clave en el log. Control: con claves falsas bien formadas, la API pasa esta comprobación y llega a la conexión. Qué no prueba: que la API vuelva a arrancar al corregirlas (solo el bloqueo, sin reinicio).
  - Previa: la conexión se abre en 15 s. Qué prueba: que una contraseña falsa generada por la prueba (nunca la real) bloquea el arranque como `conexion`. Qué no prueba: que la API vuelva a arrancar con la contraseña correcta (solo el bloqueo, sin reinicio).
  - Previa: `CANARIO_LIMITES`, si existe, tiene exactamente las reglas esperadas, con valores enteros acotados y ventanas que dividen el día (6.9). Qué prueba: que con una sola regla, con una ventana de 7 s o con un límite de 0 la API no arranca y registra `ARRANQUE BLOQUEADO: limites: <motivo>`. Control: con un valor válido, la API registra los límites configurados y llega a la conexión. Qué no prueba: que vuelva a arrancar al corregirlo (solo el bloqueo).
  - Previa: el secreto de Redis existe y tiene el formato exacto que genera `scripts/generar_secretos.py`. Qué prueba: que sin él o con un salto de línea final la API no arranca y registra `ARRANQUE BLOQUEADO: secreto_redis: <motivo>`, sin el secreto en el log. Qué no prueba: que vuelva a arrancar al corregirlo (solo el bloqueo).
  - Redis (limitador), después de la base de datos: espera hasta 15 s a que responda; sin autenticar, Redis rechaza con `AuthenticationError` (usuario `default` desactivado); `aplicacion` cuenta con `INCR` y `EXPIRE NX` en `limite:*`; y `GET`, `SCAN`, `CONFIG` y `TTL` fuera de `limite:*` dan `NoPermissionError` (ninguna modifica nada aunque la ACL las permitiera). Qué prueba: que una ACL permisiva, el usuario `default` activo y otra contraseña bloquean el arranque y, al devolver la ACL correcta, la API vuelve a arrancar. Qué no prueba: cada comando prohibido por separado en el arranque (la ACL completa se prueba aparte, `verificar_denuncia.py`, r3).
- La comprobación se hace solo al arrancar: un cambio posterior exige superusuario y se detecta en el siguiente reinicio.
- **Autenticación de PostgreSQL** (`db/pg_hba.conf`, montado y activado con `-c hba_file=/etc/postgresql/pg_hba.conf`): el `pg_hba.conf` que la imagen deja en `PGDATA` trae `trust` para el socket y el loopback (comprobado) y queda inerte. Cuatro reglas: el superusuario solo por el socket, con `peer`; `migrador`, `aplicacion` y `plataforma` solo a la base `canario`, por red, desde `samenet` y con `scram-sha-256`; el resto, `reject`. `password_encryption=scram-sha-256` va explícito en el compose, aunque en PostgreSQL 18 ya es el valor por defecto (comprobado en `pg_settings`). Pruebas (`verificar_esquema.py`, au, cada negativo con su control): `hba_file` y las cuatro reglas exactas de `pg_hba_file_rules`, sin errores ni `trust` (control: el fichero inerte de `PGDATA` sí lo tiene). Esa vista refleja el fichero en disco y no lo que el servidor cargó, así que se prueba también el comportamiento: el superusuario por TCP a `127.0.0.1` y otro rol por el socket se rechazan (control: el superusuario entra por `peer`); las contraseñas de los cuatro roles se guardan como `SCRAM-SHA-256$4096:` (control: un rol temporal con `md5` deja otro prefijo); un cliente que exige `md5` (`require_auth` de libpq) no entra porque el servidor pide SASL (control: exigiendo `scram-sha-256` sí); y `aplicacion` no llega a la base `postgres` (control: a `canario` sí).
- **Conexión de la API:** psycopg 3 con pool (máximo 5 conexiones, por debajo del `CONNECTION LIMIT 10` del rol). La contraseña se lee del fichero del secreto al abrir cada conexión; un secreto con espacios o saltos de línea es un error de configuración y bloquea el arranque, no se corrige en silencio. Cada sesión tiene `statement_timeout` de 5 s, `lock_timeout` de 2 s e `idle_in_transaction_session_timeout` de 10 s: el trigger de auditoría toma un bloqueo consultivo por empresa y el de mensajes bloquea la fila de su denuncia (6.13), y una transacción colgada bloquearía a toda la empresa o a esa denuncia. Si una petición agota `lock_timeout` o `statement_timeout`, la API responde 503 con `Retry-After` (6.11). Prueba de cada límite, con su control:
  - `statement_timeout`: una consulta de 7 s se cancela (`QueryCanceled`); control: una de 1 s termina.
  - `lock_timeout`: esperar un bloqueo consultivo ocupado falla con `LockNotAvailable` a los 2 s; control: un bloqueo consultivo libre se obtiene sin esperar. Confirma que el límite se aplica también a los bloqueos consultivos.
  - `idle_in_transaction_session_timeout`: una transacción inactiva 12 s se corta; control: una inactiva 3 s sigue abierta.
- **Contexto de empresa:** el único camino con contexto es `transaccion_empresa()`, que exige un `uuid.UUID` (un texto se rechaza antes de llegar al SQL) y lo fija con `select set_config(..., true)` y parámetro enlazado. psycopg no enlaza parámetros en `SET`, por eso no se usa. Al devolver una conexión al pool se comprueba que no lleva contexto; si lo lleva, se descarta y se registra (`error resetting connection: conexion devuelta al pool con contexto de empresa: se descarta`, sin cadena de conexión ni valor del contexto).
- **Concurrencia:** los endpoints síncronos corren en el pool de hilos de AnyIO, con un límite por defecto de 40 hilos (comprobado en el código fuente de FastAPI 0.143.0, Starlette 1.7.0 y AnyIO 4.15.1). Con 300 peticiones concurrentes el proceso no pasó de 33 hilos, por debajo de `pids_limit: 64`.
- **Límites asumidos de la conexión (decisiones conscientes):**
  - El pool no comprueba cada conexión antes de entregarla, para no añadir una ida y vuelta a la base de datos en cada petición. Si PostgreSQL se reinicia, la primera petición que reciba una conexión rota falla de forma visible y el pool la sustituye.
  - La cola de espera del pool no tiene límite: si las peticiones llegan más rápido de lo que se liberan conexiones, esperan hasta 10 s cada una. El limitador (6.9) la acota por cliente, no en total: un ataque repartido entre muchas IPs puede llenarla (8).
- La rotación de contraseñas no pasa por el script de inicialización y requiere un procedimiento propio (ver sección 11).

### 6.11 Frontera con el exterior: proxy y API

- **Redes:** la API está en la red `app` (interna, `10.88.0.0/28`), en `data` (interna, con PostgreSQL) y en `cache` (interna, con Redis). Caddy está en `app`, con la IP fija `10.88.0.2`, y en `edge` (`10.88.1.0/28`), la única red no interna, porque una red interna no puede publicar puertos. Las subredes están fuera de los rangos que Docker asigna por defecto. `ip_range` (`.8/29`) limita las IPs automáticas y reserva de `.2` a `.7` para IPs fijas: sin ello, la API arranca primero, recibe la `.2` y el proxy no puede tomarla.
- **Puertos:** el único puerto publicado es el de Caddy, `127.0.0.1:8443`, nunca `0.0.0.0` y sin puerto 80. Caddy escucha en 8443, que no es privilegiado, así que no necesita `NET_BIND_SERVICE`.
- **Caddy:** `admin off` (sin API de administración), `persist_config off` (`admin off` no desactiva el autosave de la configuración en `/config`), `auto_https disable_redirects`, `tls internal` (CA local, sin ACME) y `protocols h1` (sin listener UDP de HTTP/3 y, de forma temporal, sin HTTP/2: el binario de la imagen fijada tiene una denegación de servicio de HTTP/2 sin imagen oficial que la arregle, 6.17). Pruebas (`verificar_esqueleto.py`): Caddy solo escucha en 8443, sin API de administración en 2019 ni servidor de redirección (l, con control: un Caddy por defecto escucha también en ambos); sin autosave ni HTTP/3 (g); y todas las peticiones de f) validan el certificado contra la CA local de Caddy.
- **Host distinto de `localhost`:** responde 421 un sitio por defecto (`https://:8443`), por las rutas y con las mismas cabeceras y el mismo JSON que el resto. Sin él, la petición no casaría con ninguna ruta y Caddy respondería 200 vacío. Sustituye a `strict_sni_host on`, cuyo 421 lo genera el servidor antes de entrar en las rutas y salía con `Server: Caddy` y sin cabeceras de seguridad (comprobado). Un SNI distinto de `localhost`, o ninguno, no completa el TLS, porque no hay certificado para él (`verificar_esqueleto.py`, i).
- **Límite de cuerpo en Caddy:** `request_body max_size 128KiB`, igual que la API. `max_size` solo falla al leer el cuerpo, y por defecto `reverse_proxy` lo reenvía mientras lo lee: una petición demasiado grande llegaba a la API (comprobado: el 413 era el de la API). Con `request_buffers 129KiB`, Caddy lee el cuerpo antes de contactar con la API y corta él mismo con 413, como `client_max_body_size` en nginx. La documentación avisa de que el buffer es ineficiente con cuerpos grandes; aquí el máximo es 128 KiB por petición.
- **Plazos de Caddy:** `read_header 10s`, `read_body 30s`, `write 30s` e `idle 2m`. Por defecto, Caddy no limita la lectura del cuerpo ni la escritura ("Defaults to no timeout"): una subida que se detiene retendría la conexión, y con el buffer también su memoria (slowloris). Los 30 s dan margen a un denunciante por Tor, con poco ancho de banda, para subir 128 KiB. Pruebas: `read_body` y `read_header` por comportamiento (una subida o unas cabeceras paradas se cortan, con control; `verificar_denuncia.py`, k, y `verificar_esqueleto.py`, l); `write` e `idle` solo en la configuración que carga Caddy (`caddy adapt`, `verificar_esqueleto.py`, l), porque probarlos por comportamiento exigiría respuestas de más de 30 s o esperas de 2 minutos.
- **Errores que genera Caddy** (413, 502 con la API caída, 421): `handle_errors` y el sitio por defecto importan el mismo fragmento de cabeceras de seguridad que las respuestas normales, sin `Server`, y responden con el mismo formato JSON (`{"detalle": ...}`) que la API. Es el equivalente de `add_header ... always` en nginx.
- **Imagen de Caddy:** la oficial trae el binario con la file capability `cap_net_bind_service=ep`. Con `cap_drop: ALL` el kernel rechaza el `execve`. Se elimina con `setcap -r` en una imagen propia, en vez de devolver la capability al contenedor. `/data/caddy` (CA y clave privada) pasa de `1777` a `0700`, propiedad del usuario de Caddy. Es el único estado persistente (volumen `caddy_datos`); `/config` no se monta y queda en solo lectura.
- **API:** `GET /salud` (vivacidad, sin tocar base de datos ni Redis), las tres rutas del denunciante (6.1) y las del personal bajo `/v1/personal` (6.3). Sin `/docs`, `/redoc` ni `/openapi.json` y sin redirección de barra final. `--no-server-header`. El healthcheck no usa curl: solo da sano con 200 y el cuerpo exacto.
- **Frontera HTTP de la API** (`app/frontera_http.py`):
  - **Límite de cuerpo de 128 KiB** (segunda capa, por si la API quedara expuesta sin proxy: uvicorn no tiene límite propio). Lo aplica un middleware que lee el cuerpo entero, con la memoria acotada por el límite: rechaza por el `Content-Length` declarado sin leer nada, y cuenta los bytes reales en un envío por trozos. No depende de cómo lea FastAPI el cuerpo, que convierte en 400 cualquier excepción al leerlo salvo `HTTPException` (comprobado en el código de la versión fijada). 10 000 caracteres de texto caben con el peor escapado JSON (12 bytes por carácter fuera del plano básico).
  - **Saturación:** si una consulta agota `lock_timeout` (`55P03`) o `statement_timeout` (`57014`), la respuesta es 503 con `Retry-After: 5` y el log registra `SATURACION:` con la clase y el SQLSTATE. No es un error del servidor sino contención pasajera, y el cliente debe saber que puede reintentar. Lo hacen dos manejadores por clase de excepción; cualquier otro error de la base de datos sigue siendo un 500.
  - **Errores no previstos:** 500 genérico, y en el log solo la clase y el SQLSTATE. Hace falta un middleware propio porque el `ServerErrorMiddleware` de Starlette, aunque haya un manejador de 500, siempre vuelve a lanzar la excepción, y uvicorn volcaría el traceback con el mensaje, que puede llevar valores de la fila (comprobado en el código).
  - **422 sin eco:** el de FastAPI devuelve el campo `input` con lo que envió el cliente; el propio responde siempre `{"detalle": "petición no válida"}`. Los modelos son estrictos (`extra="forbid"`, `strict=True`) y FastAPI 0.143.0 solo interpreta como JSON un cuerpo con `Content-Type` JSON (`strict_content_type`, por defecto `True`).
  - **Formato de error único** en castellano para todas las respuestas de error, que conserva las cabeceras del error (por ejemplo `Allow` en un 405).
  - **Limitador de peticiones** (6.9), entre el middleware de errores internos y el límite de cuerpo: 429 con `Retry-After`, o 503 con `Retry-After: 5` si Redis no responde, con el mismo formato de error.
- **PostgreSQL:** `log_error_verbosity=terse`: el log del servidor no lleva `DETAIL`, que repetiría valores de la fila (por ejemplo `Key (codigo_hmac)=(...)` en un duplicado).
- **Contenedores:** usuarios no root con uid fijo (API 10001, Caddy 10002), `read_only`, `cap_drop: ALL`, `no-new-privileges`, `mem_limit` y `pids_limit`, sin tmpfs.
- **Cabeceras:** `Strict-Transport-Security: max-age=63072000` (sin `includeSubDomains` ni `preload` mientras el nombre sea `localhost`), `X-Content-Type-Options: nosniff`, `Referrer-Policy: no-referrer`, `Content-Security-Policy: default-src 'none'; frame-ancestors 'none'`, `Cache-Control: no-store`, y sin cabecera `Server`.
- **Dependencias:** versión exacta y `sha256` de todos los ficheros publicados en PyPI, instaladas con `--require-hashes` y `--only-binary :all:`. Se resuelven en un contenedor de `python:3.12-slim`, no en Windows, porque los marcadores de plataforma darían otro resultado. La imagen final no lleva pip. `fastapi` exige `opentelemetry-api`: sin SDK es una implementación vacía que no registra ni envía nada (comprobado). Imágenes base fijadas por versión y digest.
- **Salida a internet de Caddy:** la red `edge` se la da, y dentro de las opciones de red de Docker es inevitable para publicar el puerto (comprobado en Docker Desktop 29.5.3: `enable_ip_masquerade=false` no corta la salida, `gateway_mode_ipv4=isolated` exige una red interna, y en una red interna el puerto publicado no recibe nada). Caddy no la necesita: con `tls internal` crea su CA y firma sus certificados en local, sin ACME ni OCSP. Prueba (`verificar_esqueleto.py`, m): la imagen construida, con el mismo endurecimiento y un volumen vacío, en una red interna propia (control: desde esa red no se llega a `1.1.1.1:443` y desde una red normal sí), crea su CA y sirve `/salud` con TLS validado contra esa raíz, y su log no menciona `acme`, `ocsp` ni `dial`. La salida que le queda es un límite asumido (8).

### 6.12 Alta de empresas y gestión de claves

Es una operación de administración, fuera de la API pública, como el alta de inquilinos en cualquier plataforma multiempresa. La hace el servicio `gestion` de `docker-compose.yml` (`app/gestion.py`). Tiene un perfil propio, así que `docker compose up` nunca lo arranca: se ejecuta a mano con `docker compose run --rm gestion <orden>`. Está solo en la red `data` y con el mismo endurecimiento que la API.

- **Separación de roles:** `gestion` es el único servicio con el secreto de `plataforma`. La API no lo tiene, y por tanto no puede dar de alta empresas.
- **`alta-empresa`:** exige `--zona`, sin valor por defecto: quien da de alta decide el calendario de la empresa (6.5). Primero da de alta la empresa y su entrada del directorio con `plataforma` (`canal.alta_empresa(nombre, zona)`, que no toca claves). Después, con `aplicacion` y el contexto de la empresa nueva, genera su clave, la envuelve con la clave maestra y la guarda como versión 1. Son dos roles en dos sesiones, así que no hay una transacción común. Si el segundo paso falla, la salida lo dice ("NO tiene clave") y da el comando exacto para completarlo. La empresa no acepta denuncias mientras tanto.
- **`nueva-clave`:** crea la versión siguiente de la clave de una empresa. Sirve para completar un alta a medias y para rotar. Si dos ejecuciones calcularan a la vez la misma versión, la clave primaria rechazaría la segunda.
- **`suprimir-caducadas`:** aplica la supresión legal (6.14) con `plataforma`. Imprime solo recuentos por empresa y artículo, y sale con código 75 si queda alguna denuncia caducada que estaba en uso (6.14). Hay que programarla cada hora (6.14). No carga la clave maestra ni verifica la base de datos como el arranque: esas comprobaciones son las del rol `aplicacion`, y `plataforma` solo puede ejecutar la función, cuyo criterio está fijo en la base de datos.
- **`alta-admin`:** emite la invitación del primer admin de una empresa (6.3), con `aplicacion` y el contexto de la empresa, igual que `nueva-clave`. Se niega si la empresa ya tiene un admin activado, sin crear nada, y deja una fila de auditoría con actor `plataforma`. Imprime el token de invitación una sola vez: es la forma de entregarlo, porque no hay correo, y solo sirve para que su titular elija su contraseña y su TOTP. Recomienda en la salida un segundo admin.
- **`reinvitar-admin`:** recuperación de emergencia de un admin que ya estuvo activado y que nadie de su empresa puede reinvitar (6.3). Mismo rol, contexto y salida que `alta-admin`. Se niega, sin cambiar nada, si el email no es de un admin activado de esa empresa. Si actúa, desactiva la cuenta, revoca en el acto sus sesiones y dispositivos, emite la invitación y deja la fila `reinvitacion_admin_plataforma`. Se ejecuta solo tras el procedimiento fuera de banda de 6.3.
- **Antes de guardar una clave o emitir una invitación:** `gestion` aplica las mismas comprobaciones literales que el arranque de la API (6.10) y no escribe en una base de datos que no sea la esperada. Las hace con la misma sentencia que la API (`bd.SQL_SOLO_LECTURA`): en solo lectura, para que un error del código no pueda escribir, y en `REPEATABLE READ`, para que todas vean la misma foto (en `READ COMMITTED` cada sentencia vería la suya). También en solo lectura la resolución del identificador de `alta-admin` y `reinvitar-admin`; la escritura va en una transacción aparte. Prueba (`verificar_personal.py`, l): con el código real, PostgreSQL responde `on` y `repeatable read` en esos puntos (control: las transacciones de escritura de las mismas órdenes dan `off` y `read committed`). Además desenvuelve todas las claves anteriores de la empresa con la clave maestra montada. Si alguna falla, porque la clave maestra es otra o porque la clave guardada está alterada, se aborta sin crear nada.
- **Salida:** nunca imprime claves, envueltas o no. Solo identificadores y versiones. De los errores de la base de datos solo muestra la clase y el SQLSTATE, porque su texto puede incluir valores de la fila.

### 6.13 Mensajes: estado, concurrencia y tope

Las reglas que dependen del estado de la base de datos no las comprueba la API antes de insertar, porque entre comprobar e insertar el personal podría cerrar la denuncia (TOCTOU). Las impone un único trigger, `canal.preparar_mensaje()`, en el mismo `INSERT`, y la API traduce sus SQLSTATE propios (clase `CN`, que PostgreSQL no usa) sin leer el texto del error.

- **Un solo bloqueo:** el trigger bloquea la fila de la denuncia (`FOR NO KEY UPDATE`) antes que nada. Ese bloqueo serializa los mensajes de una misma denuncia (la secuencia no se repite) y choca con el `UPDATE` que cambia el estado: un mensaje que llega mientras el personal cierra la denuncia espera y ve el estado final. Es el patrón clásico de numerar los hijos bloqueando el padre. Con dos bloqueos (la fila y uno consultivo para la secuencia, como en la auditoría) habría interbloqueo entre un mensaje del denunciante y el personal que, en una transacción, escribe su mensaje y cierra la denuncia. `FOR NO KEY UPDATE` y no `FOR UPDATE`, para no chocar con el `FOR KEY SHARE` de las claves foráneas.
- **Un solo trigger:** PostgreSQL ejecuta los triggers `BEFORE` por orden alfabético de nombre. El orden de los pasos (bloqueo, estado, secuencia, tope, fecha) va dentro de una función y no depende de cómo se llamen.
- **Sin bloqueo entre empresas:** la denuncia se busca con los permisos de quien inserta y bajo RLS. Una de otra empresa es invisible, igual que una inexistente, y las dos dan el mismo error (`foreign_key_violation`, "el mensaje no corresponde a ninguna denuncia visible") sin bloquear nada. Cierra para los mensajes el límite del bloqueo consultivo antes de la RLS que sigue teniendo la auditoría (02_esquema.sql).
- **Denuncia no veraz:** una denuncia `no_veraz` (art. 32.3, 6.15) da el mismo error que una inexistente (`foreign_key_violation`), no el de cerrada: para la API no existe, y quien escribe no puede distinguirla de una suprimida (404 en los dos casos).
- **Denuncia cerrada:** `resuelta`, `archivada` e `inadmitida` no admiten mensajes (`CN001`, 409). Un expediente cerrado que acepta información que nadie leerá sería un fallo silencioso; hechos nuevos son una denuncia nueva. El personal cierra siempre con un mensaje final (6.15), que inserta antes de cambiar el estado, en la misma transacción. El seguimiento de una denuncia cerrada sigue funcionando.
- **Tope de 200 mensajes por denuncia** (`CN002`, 409): acota lo que guarda la base de datos y lo que devuelve el seguimiento, que los lee todos (como mucho 200 de 10 000 caracteres). El límite de peticiones frena la velocidad; el tope, el total.
- **Nivel de aislamiento:** la secuencia requiere que quien escribe use `READ COMMITTED` (el de la API al escribir): cada consulta del trigger ve lo confirmado por el mensaje que esperaba delante. Con un nivel superior, una secuencia repetida la rechazaría la clave primaria, nunca en silencio.
- **Contención:** si la denuncia sigue bloqueada más que `lock_timeout` (2 s), la API responde 503 con `Retry-After` (6.11).
- **Mensajes del personal:** `POST /v1/personal/denuncias/{id}/mensajes`, solo de quien tiene la denuncia asignada (6.15). Pasan por el mismo trigger, con autor `personal` y su `autor_id` dentro del AAD.

### 6.14 Supresión legal (arts. 32.4, 26.2 y 32.3 de la Ley 2/2023)

La ley obliga a borrar: a los tres meses de la recepción si no se ha iniciado la investigación (art. 32.4), en todo caso a los diez años (art. 26.2) y, sin plazo, lo que se acredite que no es veraz (art. 32.3, 6.15). Es el único borrado del sistema: el resto del esquema no tiene ningún permiso ni política de `DELETE` (`db/init/04_supresion.sql`).

- **Criterio único:** `canal.articulo_supresion(estado, fecha, zona)` decide si una denuncia se suprime hoy y por qué artículo. Iniciar la investigación es pasar a `en_instruccion`, así que el art. 32.4 alcanza a las denuncias en `nueva` (aún no se ha decidido) y en `inadmitida` (comunicación a la que no se dio curso, 6.15); el de diez años, a todas. `resuelta` y `archivada` solo se alcanzan desde `en_instruccion`: una denuncia no puede cerrarse sin investigar y escapar así del art. 32.4. Los plazos se cuentan en el calendario de la empresa, con el mismo cálculo del día que las fechas de recepción (6.5), y vencen el mismo día del mes: una denuncia del 15 de enero se suprime desde el 15 de abril. Una denuncia `no_veraz` se suprime siempre, con el artículo `art32_3` y prioridad sobre los otros dos: la evidencia dice el motivo real del borrado aunque además hubiera caducado.
- **Un único camino y fuera de la API:** `canal.suprimir_denuncias_caducadas(lote)` es de definidor y pertenece a un rol propio sin login, `propietario_supresion`. No pertenece a `propietario_funciones`: así, las funciones que usa la API no heredan el permiso de borrar. Solo la ejecuta `plataforma`, mediante `docker compose run --rm gestion suprimir-caducadas` (6.12). La API no puede borrar nada.
- **Bloquear antes de borrar:** primero bloquea las denuncias candidatas con `FOR UPDATE SKIP LOCKED` y el criterio sobre las columnas de la propia fila, y después borra mensajes, código y denuncia en sentencias separadas. Por qué:
  - Una denuncia en uso (el personal la está cambiando o llega un mensaje) no se espera, se salta, y entra en la ejecución siguiente: la supresión no aborta por la concurrencia normal ni retiene a la API.
  - En READ COMMITTED, `FOR UPDATE` vuelve a evaluar el criterio sobre la versión actual de la fila: una denuncia que acaba de pasar a `en_instruccion` deja de cumplirlo. Con el criterio en una lista calculada aparte, se borraría igual.
  - Cada sentencia posterior ve lo confirmado hasta el bloqueo, así que un mensaje confirmado justo antes se borra con su denuncia. Por eso la función exige READ COMMITTED y rechaza otro nivel.
- **Permiso de bloqueo sin permiso de modificación:** PostgreSQL exige `UPDATE` sobre alguna columna para `FOR UPDATE`. `propietario_supresion` recibe `UPDATE (estado)` con una política de `UPDATE` con `WITH CHECK (false)`: puede bloquear, pero la RLS rechaza cualquier modificación. Sin esa política, `FOR UPDATE` no da error, sino que devuelve cero filas en silencio; las pruebas lo vigilan.
- **Lotes:** como mucho 500 denuncias por llamada (100 por defecto en `gestion`), cada lote en su transacción, para caber en el `statement_timeout` y retener pocos bloqueos. `gestion` repite lotes hasta que uno vuelve vacío y después cuenta las que siguen cumpliendo el criterio: si queda alguna, es que estaba en uso, y la orden lo dice y sale con código 75. No es un error (la ejecución siguiente la suprime), así que no comparte el 1 de los errores reales: con un solo código, el programador avisaría también de lo normal, y un aviso que salta siempre acaba ignorado. El 75 es `EX_TEMPFAIL` de sysexits(3), "Temporary failure, indicating something that is not really an error", y es el que systemd.service(5) pone de ejemplo en `SuccessExitStatus=`. sysexits(3) se declara obsoleto en FreeBSD; aquí solo se toma el valor, que systemd sigue reconociendo por su nombre.
- **Evidencia anonimizada:** una fila de auditoría por denuncia suprimida, con actor `sistema`, la acción `supresion_art32`, `supresion_art26` o `supresion_art32_3` y el id de la denuncia. Es lo que permite el art. 32.4 ("dejar evidencia del funcionamiento del sistema"): un uuid aleatorio que ya no apunta a ningún dato. Sin esa fila, un borrado legítimo no se distinguiría de una manipulación.
- **Orden de bloqueos:** primero la fila de la denuncia y después el bloqueo consultivo de la auditoría de su empresa. El personal sigue el mismo orden, con sus cuentas delante: cuentas, denuncia y auditoría (6.15).
- **Frontera HTTP:** si la denuncia se suprime entre resolver el código y leerla o escribir un mensaje, la API responde el mismo 404 que a un código inexistente, no un 500. La escritura se prueba con la carrera real por HTTP: el mensaje espera al bloqueo de la supresión (`verificar_denuncia.py`, n1). La lectura no toma bloqueos y no tiene ningún punto en el que detenerla desde fuera; sus dos ramas se prueban dentro del contenedor de la API, con el código y la base de datos reales, sustituyendo solo en el proceso de la prueba la resolución del código por la de una denuncia ya suprimida (`verificar_denuncia.py`, n4).
- **Programación:** la ejecución periódica es de operación, como en cualquier tarea programada: un programador del anfitrión lanza `docker compose run --rm gestion suprimir-caducadas` **cada hora** y vigila el código de salida. En producción, un timer de systemd: `OnCalendar=hourly` con `Persistent=true` (lanza al arrancar la ejecución perdida con la máquina apagada; solo funciona con `OnCalendar=`), `SuccessExitStatus=75` y `OnFailure=` hacia una unidad que avise, que depende de la monitorización de cada despliegue. Con cron hace falta un envoltorio que distinga el 75 del resto. El Programador de tareas de Windows solo sirve en desarrollo: según el foro y el roadmap de Docker, Docker Desktop necesita una sesión de usuario abierta (sin documentación oficial que lo confirme), y sin Docker la tarea no corre. La orden lleva `-f` con la ruta absoluta del compose, para que el proyecto sea siempre el `name: canario` del fichero y no dependa del directorio desde el que se lanza. Los plazos de los arts. 32.4 y 26.2 se cuentan en días, pero el art. 32.3 pide supresión inmediata: la frecuencia es el retraso máximo entre declarar una denuncia no veraz y destruirla (mientras tanto, la API ya no la muestra a nadie). Así el secreto de `plataforma` solo existe mientras dura cada ejecución; un servicio que se quedara corriendo para programarla lo dejaría montado de forma permanente. Las unidades, la orden exacta y qué hacer con cada código de salida están en el README.

### 6.15 Instrucción: el trabajo del personal sobre las denuncias

Implementado en `app/instruccion.py` (lógica) y `app/rutas_personal.py` (transporte), bajo `/v1/personal`.

- **Quién lee el contenido (Ley 2/2023, arts. 32.1 y 8.5):** la categoría, el texto y los mensajes de una denuncia solo los lee quien la tiene asignada, sea instructor o admin. El art. 32.1 limita el acceso al Responsable del Sistema y a quien lo gestione directamente (y, si procede, a RRHH, servicios jurídicos, encargados del tratamiento y DPD); el 8.5 pide evitar el conflicto de interés, y la denuncia puede ser sobre un admin. Gestionar cuentas no da acceso al contenido. Es el modelo de GlobaLeaks: los admins configuran y los receptores leen.
- **Clasificar:** un admin ve el listado de todas las denuncias (`GET /denuncias`: id, fecha, estado y asignación; nunca categoría ni texto) y asigna (`PUT /denuncias/{id}/asignacion`). Para clasificar una que no tiene asignada se la asigna a sí mismo, la lee y, si procede, la reasigna. Cada paso deja su fila de auditoría (la asignación, con la cuenta de destino) y los demás admins la ven por la API y pueden verificar la cadena (6.7).
- **Instructor:** su listado solo trae sus denuncias asignadas. Una ajena, inexistente o de otra empresa da el mismo 404, byte a byte, en lectura, mensaje y estado: no puede saber si existe. No asigna (403).
- **Asignación:** solo a una cuenta activa y activada de la empresa (si no, 409; de otra empresa o inexistente, 404) y solo de una denuncia abierta (409). La baja de una cuenta no deshace sus asignaciones, porque eso impediría dar de baja una cuenta comprometida con denuncias abiertas; el listado marca `asignada_activa: false` para que un admin las reasigne. Asignar es idempotente: asignar a la cuenta que ya la tiene responde 204 sin escribir ni dejar fila. Un no-op auditado sería ruido y una forma de inundar una auditoría que no se puede borrar.
- **Estados:** tabla literal de transiciones. `nueva` pasa a `en_instruccion` (iniciar la investigación) o a `inadmitida` (no se da curso, art. 32.4); `en_instruccion`, a `resuelta` o `archivada`; cualquiera de los cinco, también los cerrados, a `no_veraz` (abajo). Los estados cerrados no cambian salvo a `no_veraz`. Cualquier otra transición da 409 sin cambiar nada. `inadmitida` existe para que una comunicación a la que no se da curso siga sujeta a la supresión de los tres meses (6.14): archivarla sin investigar la conservaría diez años.
- **Mensaje final obligatorio:** cerrar (`resuelta`, `archivada`, `inadmitida`) exige un mensaje para el denunciante (422 si falta). Una denuncia cerrada no admite mensajes (6.13), y sin él el denunciante nunca sabría el resultado (art. 9.2.d, dar respuesta). El mensaje se inserta antes del cambio de estado, en la misma transacción.
- **Lo que ve cada uno de un mensaje:** el personal ve `autor_id` (quién del personal escribió); el denunciante, solo `personal` (6.1).
- **Comprobación de la cuenta en cada acción:** la sesión se autentica en su propia transacción (6.3). Para que una baja confirmada entre autenticar y actuar no deje actuar a una cuenta ya dada de baja (TOCTOU), cada acción vuelve a comprobar en su transacción que la cuenta sigue activa y activada, y la bloquea con `FOR KEY SHARE`. Es el modo que solo choca con `FOR UPDATE`, el que toman la baja, el cambio de contraseña y la recuperación, y no con `FOR NO KEY UPDATE`, el del `UPDATE` de los contadores del login (PostgreSQL 18, tabla 13.3). Con `FOR SHARE`, unos logins fallidos contra el email de quien instruye retrasarían cada una de sus acciones. Si la baja confirma mientras la acción espera, PostgreSQL vuelve a evaluar el `WHERE` sobre la versión nueva de la fila (`READ COMMITTED`), no encuentra una cuenta activa y la acción no actúa: 401 (comprobado con el código real, tabla 7). Una baja dura milisegundos; si algo retuviera la cuenta más que `lock_timeout` (2 s), la acción daría 503 sin actuar. Los listados, de solo lectura, comprueban la cuenta en la misma foto que la consulta.
- **Una denuncia ajena no se bloquea nunca:** la asignación va dentro del `WHERE` de la consulta que bloquea la denuncia, así que quien no la tiene asignada obtiene cero filas y no bloquea nada (ni retiene los mensajes del denunciante, que esperan a ese bloqueo). La documentación de PostgreSQL dice que se bloquean "the rows retrieved" sin decir nada explícito de las que no cumplen el `WHERE`; por eso se comprueba con el SQL real (tabla 7).
- **Lectura consistente:** `FOR SHARE` sobre la denuncia choca con el bloqueo del trigger de mensajes y con el cambio de estado, así que la denuncia y sus mensajes salen de la misma foto. No se usa `REPEATABLE READ` porque la lectura escribe su fila de auditoría, y el encadenado necesita `READ COMMITTED`. Se descifra después de confirmar, para no retener la conexión.
- **Orden de bloqueos:** cuentas, denuncia y auditoría, el mismo que el personal (6.3) y la supresión (6.14). Asignar bloquea varias cuentas, y lo hace en el mismo orden que la baja y la recuperación: primero todos los admins activos por id y después la cuenta de destino. Con otro orden (por ejemplo, las dos cuentas por id), una asignación y una baja simultáneas podrían interbloquearse: la baja toma los admins y después la cuenta objetivo.
- **Listado paginado:** de 100 en 100, de la más reciente a la más antigua, con un cursor `<fecha>.<id>` de forma exacta y un filtro opcional por estado; un cursor o un estado mal formados dan 422.
- **Sin log en el flujo normal:** las acciones quedan en la auditoría, que no lleva hora. La única excepción es la declaración de no veraz (abajo).
- **No veraz (art. 32.3):** "si se acreditara que la información facilitada o parte de ella no es veraz, deberá procederse a su inmediata supresión", salvo que la falta de veracidad pueda ser delito (entonces se conserva para el procedimiento judicial).
  - **Quién:** solo un admin con la denuncia asignada (`POST /denuncias/{id}/estado` con `no_veraz`). Un instructor recibe 403 antes de tocar la base de datos; un admin sin la asignación, el 404 de siempre. Es la decisión del Responsable del Sistema que destruye un expediente, no la de quien solo instruye.
  - **Desde cualquier estado:** la falta de veracidad puede acreditarse después de resolver. Es terminal.
  - **Sin mensaje** (422 si lo trae): nadie lo leería, porque el denunciante deja de ver la denuncia.
  - **Bloqueo inmediato en la API, destrucción en la supresión:** desde la declaración, una `no_veraz` no existe para la API. Cada consulta del personal (lectura, mensaje, estado, asignación y listado) y la del seguimiento la excluyen en su propio `WHERE` y dan el mismo 404 que una inexistente; el trigger de mensajes la rechaza como no visible (6.13); el filtro del listado no la admite (422). La borra la siguiente ejecución de `suprimir-caducadas` (6.14, `art32_3`), con sus mensajes, su código y su fila de evidencia. Así la API sigue sin poder borrar nada y el borrado sigue teniendo un único camino: la alternativa (una función de definidor que la API pudiera ejecutar) le habría dado a la API un permiso de borrado y obligado a rehacer las comprobaciones de arranque.
  - **Por qué no una RLS que la oculte:** una política que escondiera las `no_veraz` rompería el propio `UPDATE` que la declara ("new row violates row-level security policy", comprobado en la imagen fijada). El filtro va en cada consulta, escrito en cada una, para que no dependa de que nadie lo olvide en una consulta nueva.
  - **Rastro:** la fila `estado_no_veraz` de la auditoría (con el admin como actor), la de `supresion_art32_3` al destruirla y una línea `EVENTO declaracion_no_veraz` en el log de la API con empresa, cuenta y denuncia, sin contenido. El evento existe porque la destrucción no tiene vuelta atrás: el abuso (un admin que entierra denuncias) debe dejar una señal fuera de la base de datos que la empresa administra. Lleva hora, pero es una acción del personal, no del denunciante (6.5).
  - **Excepción penal:** si los hechos pueden ser delito, el admin no la declara no veraz; la conserva y la remite al Ministerio Fiscal (art. 9.2.j). El sistema no tiene un estado propio para esa retención (8).

### 6.16 Inyección SQL y validación de la frontera

La referencia es el SQL Injection Prevention Cheat Sheet de OWASP: consultas parametrizadas como defensa principal, lista cerrada para lo que no se puede parametrizar y mínimo privilegio como red. Se prueba con `tests/security/verificar_inyeccion.py`, que sigue WSTG-INPV-05.

- **Qué demuestra cada prueba:** la defensa es la parametrización, y lo que la sostiene es la estructura del código, no una lista de ataques. El análisis estático y el del catálogo son exhaustivos: recorren todas las llamadas que ejecutan SQL y todas las funciones plpgsql, y fallan ante lo que no saben resolver. Los payloads son un muestreo: que ninguno funcione no demuestra que no exista inyección, solo que con esta batería no se ha encontrado ninguna. Límites del análisis estático: reconoce las llamadas por su nombre (`execute`, `executemany`, `copy`, `stream`), así que no ve SQL ejecutado por otro camino (por ejemplo con `getattr`) ni fuera de `app/`. Por eso un cambio en el acceso a datos también pasa por revisión de código.

- **Todo el SQL es literal:** cada `execute` de `app/` recibe un literal o una constante de módulo que es un literal puro, y los valores van siempre como parámetros. No hay `psycopg.sql`, ni SQL compuesto con f-strings, `%`, `format` o concatenación, ni `ClientCursor` (que enlazaría los parámetros en el cliente). Lo comprueba un análisis del árbol sintáctico que falla cerrado: lo que no sabe resolver es un fallo.
- **Ninguna función de la base de datos compone SQL:** ninguna función plpgsql usa `EXECUTE` dinámico.
- **Lo que no se puede parametrizar va por lista cerrada:** el estado del listado se compara con la lista de estados; el cursor, el identificador de empresa de la ruta y los ids se analizan con su forma exacta (fecha y uuid, 32 hexadecimales, uuid) antes de llegar al SQL. No hay `ORDER BY`, `LIMIT` ni nombres de columna que dependan de la entrada, ni `LIKE`.
- **Entradas que llegan al SQL como texto:** la empresa y el email del login (la empresa se consulta siempre, también mal formada, para que el trabajo sea el mismo en todos los caminos, 6.3), el email de una invitación y, en `gestion`, el nombre de la empresa y el email del admin. Todas como parámetro.
- **Validación de la frontera (`app/validacion.py`):** todo campo de texto de un modelo de entrada es `TextoLinea` (identificadores, emails, contraseñas, tokens y códigos: sin caracteres de control ni surrogates) o `TextoLibre` (textos de denuncias y mensajes: solo rechaza lo que no es texto representable). Los dos rechazan el NUL, que PostgreSQL no admite en un texto, y los surrogates sueltos, que JSON permite escribir pero no son caracteres Unicode (RFC 8259, 8.2). El rechazo es el 422 propio, sin eco. Antes de este tipo, un NUL en el email del login o de una invitación daba un 500 que se podía provocar sin credenciales, y en los textos se cifraba y se guardaba. Pydantic ya rechazaba los surrogates en los campos con límite de longitud, pero no en los que no lo tienen (el código de seguimiento): era un efecto lateral y no una garantía. La batería recorre los modelos con el código real y exige que cada campo de texto use uno de los dos tipos: un campo nuevo con un `str` sin más la hace fallar (cerrado por construcción).
- **Por qué el texto libre admite caracteres de control:** el texto de una denuncia es una prueba y se guarda tal cual, como en los canales de denuncia de referencia. Un texto pegado desde un procesador de textos puede llevar un salto de página o un salto manual (`\x0c`, `\x0b`), y rechazarlo con un 422 genérico podría hacer perder una denuncia legítima. Lo que esos caracteres pudieran inyectar al mostrarse (por ejemplo una secuencia de terminal con ESC) se resuelve en la salida, como pide OWASP (Cross Site Scripting Prevention Cheat Sheet: escapar según el contexto al mostrar): la API devuelve los controles C0 escapados en el JSON (RFC 8259, 7), así que nunca salen como bytes en crudo, y escapar al mostrar es tarea del cliente (8). En un identificador, un email, una contraseña, un token o un código no tienen ningún uso legítimo, y ahí sí se rechazan.
- **Una sola regla de email:** `validar_email` (ASCII imprimible, sin espacios, con `@` después del primer carácter, en minúsculas) la usan la API y `gestion`. Antes, `gestion` aceptaba un email con espacios o no ASCII que la API habría rechazado. `gestion` rechaza también un nombre de empresa con caracteres de control.
- **El identificador de empresa del login no se valida como 32 hexadecimales en la frontera, a propósito:** una empresa mal formada debe dar el mismo 401, byte a byte, que una inexistente (6.3). Un 422 distinto rompería esa uniformidad.
- **Mínimo privilegio:** si aun así alguien ejecutara SQL como `aplicacion`, no puede leer ficheros del servidor (`pg_read_file`, `lo_import`), ejecutar programas (`COPY ... TO PROGRAM`), leer `pg_authid`, crear objetos en `public` ni en `canal`, borrar tablas, cambiar su rol ni crear extensiones. El límite que queda está en 8 (fijar la variable de empresa).

### 6.17 Cadena de suministro y escaneos

Lo que se ejecuta en producción viene de terceros: imágenes base, paquetes de PyPI y el binario de Caddy. La defensa tiene dos partes: fijar exactamente qué se usa y escanearlo de forma repetible. Se prueba con `tests/security/verificar_escaneos.py`.

- **Herramientas fijadas por versión y digest:** Trivy 0.74.0, gitleaks 8.30.1, pip-audit 2.10.1 y bandit 1.9.4. En marzo de 2026 se comprometió la cadena de publicación de Trivy (GHSA-69fq-xp46-6x23): el binario 0.69.4 y las imágenes 0.69.5 y 0.69.6 eran maliciosas y se distribuyeron moviendo etiquetas. Por eso ninguna herramienta se usa por etiqueta. Antes de fijar cada digest se comprobó que es el mismo en Docker Hub y en GHCR, y en Trivy además la firma cosign con la identidad exacta del workflow de release de esa etiqueta (`reusable-release.yaml@refs/tags/v0.74.0`), no con el patrón genérico de su documentación. gitleaks no firma sus imágenes (8).
- **Periodo de espera de 14 días:** no se adopta una versión publicada hace menos de 14 días, ni en las herramientas ni en sus dependencias transitivas (cinco se fijaron a la versión anterior). Los compromisos como el de Trivy se detectan en horas o días. La excepción, como en Dependabot, son las imágenes de ejecución que publican arreglos de seguridad: Caddy 2.11.7 tenía 9 días y se mantiene.
- **Las herramientas con mínimo privilegio:** cada una corre en un contenedor desechable con raíz de solo lectura, sin capacidades, sin escalada y como `nobody`. Ninguna recibe el socket de Docker, que equivaldría a root en el anfitrión: las imágenes se les pasan exportadas con `docker save`. Ninguna recibe secretos ni el directorio `secrets/`. Los escaneos de Trivy y gitleaks corren sin red; solo descargan con red la base de datos de Trivy (del repositorio oficial, explícito) y los avisos de OSV.
- **Secretos en Git (gitleaks):** se escanean dos cosas. El historial, montando solo `.git` en solo lectura. Y lo que se podría commitear (lo seguido y lo nuevo no ignorado), copiado a un directorio temporal **sin** `secrets/`: las baterías se ejecutan antes del commit, así que escanear solo el historial dejaría fuera justo lo que está por entrar. La salida va enmascarada (`--redact`). Además, Git solo sigue `.gitkeep` y `README.md` en `secrets/`.
- **Dependencias de Python:** pip-audit consulta OSV (que agrega los avisos PYSEC y GHSA) sobre `requirements.txt`. La integridad la comprueba pip, no pip-audit: con `--disable-pip`, pip-audit solo exige que haya hash, no que sea válido (comprobado en su código fuente y con un hash alterado que no detecta). Por eso la batería descarga los wheels con `pip download --require-hashes`, igual que al construir la imagen.
- **Análisis estático:** bandit sobre `app/` sin hallazgos de severidad media o alta y sin ningún `# nosec`: uno nuevo hace fallar la batería y obliga a revisarlo.
- **Imágenes (Trivy):** vulnerabilidades y secretos de las cuatro imágenes (api, caddy, postgres y redis; `gestion` es la misma imagen que la API). Falla cualquier HIGH o CRITICAL con arreglo publicado que no esté declarada como no explotable, y cualquier secreto. Las que no tienen arreglo se listan en cada ejecución y son riesgo residual (8). Trivy también revisa los tres Dockerfiles, con las comprobaciones que trae el binario fijado (no descarga otro artefacto que cambie).
- **PostgreSQL sin gosu:** la imagen oficial trae `gosu` (compilado con Go 1.24.6: una CRITICAL y 24 HIGH con arreglo) solo para que el entrypoint baje de root a `postgres`. Aquí el contenedor nunca arranca como root, así que nunca se ejecutaba. En vez de aceptar la excepción se quita la causa: `db/Dockerfile` borra el binario y declara `USER 70:70` en la propia imagen (Trivy marcaba la imagen como root por defecto, DS-0002). Si alguien la arranca como root, el entrypoint falla de forma visible en lugar de bajar de privilegios en silencio.
- **Caddy y VEX:** el binario de la imagen fijada lleva Go 1.26.8 y `golang.org/x/net` 0.59.0, con tres denegaciones de servicio arregladas en Go 1.26.9 y sin imagen oficial que las traiga (el digest fijado es el último publicado). Compilar Caddy por nuestra cuenta sería una cadena de construcción propia fuera de la imagen oficial firmada: más superficie, no menos. Se declara cada una en `tests/security/canario.openvex.json` (OpenVEX, el formato estándar para afirmar que una vulnerabilidad no es explotable, que Trivy aplica de forma nativa), y solo después de quitar o demostrar inalcanzable el código vulnerable:
  - CVE-2026-78669 (tramas SETTINGS de HTTP/2): **alcanzable**, así que se quita HTTP/2 (`protocols h1`). Una API sin frontend no pierde nada con HTTP/1.1 y el reenvío a la API ya lo era. Comprobado: la configuración adaptada solo lleva `h1` y Caddy elige `http/1.1` aunque el cliente ofrezca `h2` (control: un Caddy con `h1 h2` elige `h2`).
  - CVE-2026-78667 (cabeceras Range en `FileServer` y `ServeContent`): no alcanzable, porque solo se usan `reverse_proxy` y `respond` (control: un `file_server` aparece en la configuración adaptada).
  - CVE-2026-97031 (ECH en `crypto/tls`): no alcanzable. En el código de Go 1.26.8, sin claves ECH el servidor devuelve el ClientHello exterior antes de procesar las referencias vulnerables, y Caddy 2.11.7 solo instala claves con la opción global `ech` (control: con `ech`, la configuración adaptada lleva `encrypted_client_hello`).

  Cada declaración está **atada a la versión exacta** del componente (`pkg:golang/stdlib@v1.26.8` dentro de la raíz `pkg:golang/caddy`): con la versión siguiente no suprime nada, así que una imagen nueva se vuelve a evaluar sola. Cada una **caduca a los 30 días** (la batería falla y obliga a revisarla) y una declaración que ya no suprime nada también falla, para que se retire y se vuelva a `protocols h1 h2`.
- **SBOM:** un CycloneDX por imagen en cada ejecución (fuera del repositorio, en el directorio temporal del sistema). Ante un CVE nuevo, "¿lo llevamos?" se contesta buscando en él.
- **Un escaneo es una foto:** el resultado vale el día que se ejecuta, porque cada día se publican vulnerabilidades nuevas. En operación, la batería se ejecuta de forma periódica (8), con el mismo modelo que la supresión (6.14): un programador del anfitrión la lanza y vigila el código de salida. La batería registra las versiones de las herramientas y la fecha de la base de datos de Trivy para poder reproducir cada resultado.

### 6.18 Redacción: suprimir una parte del texto (arts. 32.2 y 29 de la Ley 2/2023)

El art. 32.2 obliga a suprimir de inmediato los datos personales que no sean necesarios para conocer e investigar los hechos y, de inmediato también, los de categorías especiales: "Si la información recibida contuviera datos personales incluidos dentro de las categorías especiales de datos, se procederá a su inmediata supresión, sin que se proceda al registro y tratamiento de los mismos". El art. 29 pide eliminar "sin dilación indebida" lo recopilado por accidente. Son datos dentro de una denuncia, no la denuncia: borrarla entera por una frase destruiría también lo que sí hay que investigar. Implementado en `app/instruccion.py`, `app/rutas_personal.py` y `db/init/05_redaccion.sql`.

- **Cómo lo resuelve la industria:** GlobaLeaks tacha por rangos. El cliente envía posiciones, el servidor sustituye cada carácter por U+2588 y cada cambio queda en su registro (`backend/globaleaks/handlers/recipient/rtip.py`, rama `stable`, función `redact_content`). Canario sigue ese modelo sin su paso previo de marcar (8).
- **Quién:** solo un admin con la denuncia asignada, como la declaración de no veraz (6.15): destruye una parte de la prueba sin vuelta atrás. Un instructor recibe 403; un admin sin la asignación, de otra empresa, o con una denuncia `no_veraz`, el 404 de siempre. Vale en cualquier otro estado, también en los cerrados (un dato sobrante puede verse después de resolver), sobre el texto de la denuncia (`POST /v1/personal/denuncias/{id}/redaccion`) o de cualquier mensaje (`POST .../mensajes/{secuencia}/redaccion`), sea del denunciante o del personal. La categoría no se redacta: es de una lista cerrada.
- **Qué se envía:** de 1 a 50 tramos, cada uno con su posición (`desde`, en caracteres: code points) y el texto exacto que tacha (`texto`). Si en esa posición no está ese texto, 409 y no se escribe nada; si un tramo falla, no se aplica ninguno. El motivo: la redacción es destructiva, y un cliente que contara en otra unidad tacharía un trozo desplazado y dejaría ver parte del dato. Es el fallo que describe el propio código de GlobaLeaks ("leak the leading character(s) of the redacted value"): un navegador cuenta en UTF-16 y un emoji antes del tramo lo desplaza una posición. Con el texto esperado, cualquier desajuste falla de forma visible (probado con la posición en UTF-16: 409).
- **El resultado:** cada carácter tachado pasa a ser `█`. El texto conserva su longitud, así que las posiciones del resto no cambian entre una redacción y la siguiente. El personal y el denunciante ven el texto tachado: es la única copia que queda en la base de datos viva.
- **Cifrado:** la API descifra, tacha y vuelve a cifrar con la versión actual de la clave de la empresa y el mismo AAD (6.4), con la denuncia bloqueada (`FOR NO KEY UPDATE`, el bloqueo del trigger de mensajes): nadie cambia el contenido entre leerlo y escribirlo.
- **La escritura es una función, no un permiso de la API:** `aplicacion` sigue sin `UPDATE` sobre el contenido cifrado (6.2). Lo reescriben `canal.redactar_denuncia()` y `canal.redactar_mensaje()`, de definidor y con un dueño propio sin login, `propietario_redaccion` (ni las funciones de la API ni la supresión heredan ese permiso). Cada función:
  - comprueba por su cuenta que quien actúa es un admin activo y activado de la empresa del contexto y que tiene la denuncia asignada, y que no es `no_veraz`. La API ya lo ha comprobado; esto la protege de un error de lógica, no de una API comprometida (que podría pasar el id del admin asignado);
  - escribe solo si el contenido sigue siendo exactamente el que la API leyó (compare-and-swap);
  - deja la fila de auditoría en la misma sentencia (`redaccion_denuncia`, o `redaccion_mensaje` con el id del mensaje como destino). Ni una API comprometida reescribe un contenido sin dejar rastro.
  Sus errores (`CN003` y `insufficient_privilege`) no deberían darse nunca, porque la API comprueba lo mismo antes con la fila bloqueada: si se dan, son un 500 visible.
- **Idempotente:** pedir que se tache lo que ya está tachado responde 204 sin escribir ni dejar fila, como la asignación (6.15): un cambio vacío auditado sería ruido en una auditoría que no se puede borrar.
- **Rastro:** la fila de auditoría y una línea `EVENTO redaccion` en el log de la API, con empresa, cuenta, denuncia, mensaje y, por cada tramo, su posición y su longitud, nunca el texto. Existe por lo mismo que la de no veraz (6.15): el abuso (un admin que tacha lo que le incrimina) debe dejar una señal fuera de la base de datos que la empresa administra; y es el registro que permite volver a tachar lo mismo si se restaura una copia (8).
- **Qué se tacha lo decide la empresa:** el sistema no detecta datos de salud o de orientación sexual en un texto libre. Tampoco decide si un dato de categoría especial que es el propio objeto de la denuncia (una discriminación por salud) debe suprimirse: el art. 32.2 no hace esa excepción, y no se ha encontrado un criterio de la AEPD que la aclare. Es una decisión del Responsable del Sistema con su DPD (9).

## 8. Límites asumidos

Estos límites se documentan, no se esconden:

- **Servidor completamente comprometido** con acceso a la clave maestra: el atacante puede descifrar.
- **Claves en memoria:** Python no permite borrar con garantías un valor de la memoria. La clave maestra, la del HMAC y las claves de empresa desenvueltas viven en el proceso de la API mientras está en marcha.
- **Límite de cifrados por clave:** NIST SP 800-38D (8.3) limita cada clave a 2^32 cifrados con nonce aleatorio. El código no lleva la cuenta; si una empresa se acercara, se rota su clave (6.12).
- **Alta con otra clave maestra:** en el alta no hay claves anteriores con las que contrastar la clave maestra. Si la del servicio `gestion` fuera distinta de la de la API (los dos montan el mismo fichero de `secrets/`, así que exige un error manual), la empresa nueva tendría una clave que la API no puede desenvolver. No pasaría en silencio: la primera denuncia fallaría con un error de integridad visible.
- **Relleno:** el tamaño del cifrado revela el tramo de 256 bytes en que cae el texto, no su longitud exacta.
- **Orden de inserción en la base de datos:** la fecha al día protege a quien lee las filas, no frente a un análisis forense con acceso directo a PostgreSQL: `xmin` y el orden físico de las filas permiten reconstruir en qué orden se insertaron.
- **El límite es por cliente, no global:** un ataque repartido entre muchas IPs no lo frena, y puede llenar la cola del pool de conexiones (6.10). Un límite global por ruta o por empresa lo acotaría, pero le daría a cualquiera la forma de dejar sin canal a todas las empresas, o a una concreta (el identificador público no es secreto), con unas pocas peticiones por segundo. Se prefiere que un ataque distribuido degrade el servicio a que uno pequeño lo cierre.
- **Tor y NAT:** muchos usuarios de Tor salen por el mismo nodo, y detrás de un NAT muchas personas comparten IP: comparten contador. Por eso los límites son moderados. GlobaLeaks añade una prueba de trabajo por petición, que no depende de la IP; aquí queda como "diseñado, no implementado".
- **Ventana fija:** en la frontera entre dos ventanas se admite hasta el doble del límite. La ventana deslizante lo evita a cambio de más memoria y más operaciones por petición.
- **Reiniciar la API reinicia los contadores:** la sal es nueva en cada proceso, así que tras un reinicio cada cliente empieza de cero. Un atacante no puede provocar el reinicio desde fuera.
- **Un solo proceso:** uvicorn arranca un único proceso (Dockerfile, sin `--workers`). Con varios, cada uno tendría su sal y el límite efectivo se multiplicaría por el número de procesos; habría que compartir la sal entre ellos. Una prueba lo vigila: en el contenedor de la API solo hay un proceso de Python, el 1 (control: la misma imagen con `--workers 2` muestra sus procesos hijos) (`verificar_denuncia.py`, r4).
- **Memoria de Redis:** con `noeviction` y 64 MB, si un ataque distribuido llenara la memoria con contadores, Redis rechazaría las escrituras y la API respondería 503 a todos (falla cerrado) hasta que caducaran, como mucho en una hora.
- **Sin línea por 429:** el log no registra los rechazos por límite (6.5), así que no hay visibilidad de un ataque por fuerza bruta en curso más allá de los eventos de Redis no disponible.
- **Tope de mensajes:** una conversación de más de 200 mensajes exige una denuncia nueva. Es un límite deliberado (6.13).
- **Fecha calculada en tres sitios:** denuncia, mensaje y auditoría calculan el día con su propia copia de la misma expresión, para no dar `EXECUTE` sobre una función común a cada rol que inserta (6.5). Cambiar una sin las otras lo detecta `verificar_esquema.py`, z. El "hoy" de la supresión (6.14) es una cuarta copia; sus pruebas fijan los bordes en el día de la zona de la empresa, pero no con una zona en la que sea otro día.
- **La auditoría sobrevive a la supresión:** conserva los ids del personal que actuó sobre una denuncia más allá de los diez años del art. 26.2, y el id de cada denuncia suprimida. La auditoría es inmutable y encadenada: anonimizar esas filas rompería la cadena.
- **La supresión hay que programarla:** la función no se ejecuta sola. Sin una ejecución periódica de `gestion suprimir-caducadas` (cada hora, en el anfitrión), los plazos no se cumplen. Cómo programarla se documenta en el README (6.14).
- **Una ejecución que no ocurre no avisa:** vigilar el código de salida detecta la ejecución que falla, no la que nunca llega a correr (máquina apagada, Docker parado, tarea borrada). `Persistent=true` recupera la ejecución perdida al arrancar, pero si el anfitrión entero falla, cualquier comprobación que corra en él falla con él. En producción hace falta una alerta por ausencia (la que salta cuando deja de llegar la señal de éxito) desde fuera del anfitrión; depende de la monitorización de cada despliegue y este repositorio no la trae.
- **El nombre del proyecto se puede pisar:** Docker Compose da prioridad a `-p` y a la variable `COMPOSE_PROJECT_NAME` (también desde un `.env`) sobre el `name: canario` del fichero, y el nombre es el prefijo de los volúmenes. Con otro nombre, la pila arranca sobre una base de datos nueva y vacía sin ningún error, y una supresión programada actuaría sobre otra base de datos (comprobado con `docker compose config`, 11). Por eso el repositorio no trae `.env.example` ni usa `.env`; quien opere no debe fijar esa variable en el anfitrión ni en el entorno del programador.
- **"Inmediata" significa "en la siguiente ejecución":** una denuncia declarada no veraz deja de existir para la API en el acto, pero sigue en la base de datos (cifrada) hasta que corre la supresión: como mucho una hora si se programa como se indica. Con una programación diaria, el retraso sería de un día; sin programación, nunca se destruiría y el art. 32.3 quedaría reducido a un bloqueo.
- **No veraz sin cuatro ojos:** la declara un solo admin con la denuncia asignada, y la destrucción no tiene vuelta atrás. La auditoría y el `EVENTO declaracion_no_veraz` hacen visible el abuso, no lo impiden. Un segundo admin que confirme exigiría un estado intermedio y su flujo; diseñado, no implementado.
- **No veraz en parte:** el art. 32.3 habla de la información "o parte de ella". La denuncia entera se declara no veraz (6.15); si solo es falsa una parte, se tacha con la redacción (6.18). La fila `redaccion_denuncia` no dice el motivo (art. 32.2 o 32.3).
- **Redacción sin cuatro ojos:** la hace un solo admin con la denuncia asignada y no tiene vuelta atrás. La auditoría y el `EVENTO redaccion` hacen visible el abuso (tachar lo que incrimina a quien tacha), no lo impiden. GlobaLeaks separa el permiso de marcar del de tachar; un segundo admin que confirme queda diseñado, no implementado.
- **La base de datos no puede comprobar que solo se tachó:** el contenido está cifrado, así que `redactar_denuncia` y `redactar_mensaje` no pueden ver si el texto nuevo es el antiguo con `█`. Una API comprometida podría escribir otro texto, pero siempre con su fila de auditoría (6.18).
- **Se ve la longitud de lo tachado:** cada carácter pasa a ser un `█`, como en GlobaLeaks, para que las posiciones no se muevan. La longitud de un nombre tachado sigue a la vista.
- **Qué tachar lo decide una persona:** el sistema no detecta datos de salud o de orientación sexual en un texto libre, ni decide si un dato de categoría especial que es el objeto de la denuncia debe suprimirse (9).
- **El borrado es de la base de datos viva:** la supresión (6.14) y la redacción (6.18) quitan los datos de las tablas, no del disco. PostgreSQL 18 (24.1.2): "an UPDATE or DELETE of a row does not immediately remove the old version of the row"; `VACUUM` "marks the space available for future reuse", sin decir que lo sobrescriba. El WAL y las copias de seguridad conservan la denuncia, o el texto antes de tacharlo, y son legibles con la clave maestra, porque la clave de cada empresa está en la misma copia, envuelta (6.4). Por eso la copia de la clave maestra se guarda separada de las de la base de datos (README). El borrado criptográfico (una clave por denuncia que se destruye) queda diseñado, no implementado, y solo serviría con esas claves fuera de las copias.
- **Restaurar una copia deshace supresiones y redacciones:** las denuncias caducadas se vuelven a suprimir solas, porque el criterio es su estado y su fecha (`canal.articulo_supresion`); las declaradas no veraces y las redacciones posteriores a la copia vuelven a aparecer. El EDPB (informe del Coordinated Enforcement Framework de 2025 sobre el derecho de supresión, febrero de 2026, pág. 21) lo admite en las copias, con una condición: "organisations should have appropriate procedures to keep track of erasure requests and comply with them on restored systems, as much as possible". Aquí el registro son las líneas `EVENTO declaracion_no_veraz` y `EVENTO redaccion` del log de la API (6.15 y 6.18), y el procedimiento está en el README. Dos requisitos y un límite:
  - El log de la API tiene que salir del anfitrión y conservarse al menos tanto como las copias. Hoy el compose lo rota en 3 ficheros de 10 MB: sin ese envío, el registro se pierde antes que la copia.
  - Es manual: alguien tiene que hacerlo tras restaurar, y mientras tanto esas denuncias vuelven a verse.
  - Si la API se cae entre confirmar la transacción y escribir la línea de log, esa acción no queda registrada. Un registro propio en la base de datos de gestión, con una orden que lo vuelva a aplicar, queda diseñado, no implementado.
- **Sin estado de retención judicial:** la excepción penal del art. 32.3 se cumple no declarando la denuncia no veraz. Si además es antigua, la supresión de los arts. 32.4 y 26.2 la alcanzaría igual: conservarla para un procedimiento judicial más allá de esos plazos exigiría un estado que la excluya, con su control; diseñado, no implementado.
- **El 503 revela que el identificador existe:** una empresa sin clave responde 503 y no 404. El identificador público no es secreto (lo reparte la empresa, 6.3) y es un estado operativo anómalo; un "inténtelo más tarde" es mejor para quien intenta denunciar que un "no existe".
- **Tiempo de respuesta:** un código o identificador mal formado se rechaza sin consultar la base de datos. El tiempo distingue "mal formado" de "bien formado pero inexistente", y eso solo revela si el formato es válido, que es público.
- **Rotar `clave_hmac_codigos` invalida todos los códigos:** sus HMAC ya no coincidirían. Diseñado, no implementado: varias claves de HMAC con versión.
- **Reintentos:** si la conexión se corta después de crear la denuncia y antes de recibir el código, el denunciante puede reintentar y crear otra con otro código.
- **El texto se guarda tal cual:** es una prueba y no se modifica. Solo se rechazan el NUL y los surrogates, que no son texto representable (6.16); los caracteres de control y los de formato, como ESC o el control bidi U+202E, se guardan. La API los devuelve escapados en el JSON; escaparlos al mostrarlos es tarea del cliente.
- **Memoria del buffer de Caddy:** cada petición en vuelo puede retener hasta 129 KiB en Caddy (`mem_limit` de 128 MB), y como mucho 30 s (`read_body`). El limitador lo acota por cliente, pero Caddy lee el cuerpo antes de que la API cuente la petición.
- **Lectura del cuerpo en uvicorn:** uvicorn no tiene plazo propio para leer el cuerpo. Detrás de Caddy no importa (Caddy lo lee entero antes de reenviarlo); si la API quedara expuesta sin proxy, una subida lenta retendría un hilo.
- **Inyección SQL completa:** RLS por variable de sesión protege de errores de lógica y de filtros olvidados, pero quien lograra ejecutar SQL arbitrario podría fijar él mismo la variable de empresa. La defensa real es no permitir esa inyección (consultas parametrizadas) y limitar los privilegios del rol de la API.
- **Observador de red:** la IP del denunciante es visible para su proveedor y para el servidor en la conexión. La mitigación real es acceder por Tor, fuera del alcance de esta API.
- **Cifrado de extremo a extremo:** no implementado. El servidor descifra contenido para servirlo al personal. Plataformas como GlobaLeaks usan cifrado de cliente; aquí queda como mejora futura.
- **Autoidentificación:** si el denunciante escribe datos que lo identifican en el texto, el sistema no puede evitarlo.
- **Pérdida del código:** sin recuperación.
- **Disponibilidad:** una caída de Redis implica rechazo temporal de peticiones (6.9).
- **Quien opera `gestion` tiene todos los secretos:** monta la contraseña de `aplicacion` y la clave maestra. Las restricciones de `alta-admin` (solo sin admins activados) y de `reinvitar-admin` (solo sobre un admin activado), sus filas de auditoría y una revocación que el titular nota en el acto hacen visible un abuso, no lo impiden. Impedirlo exige custodia de claves fuera del anfitrión (un HSM o un gestor de secretos con aprobación), fuera del alcance.
- **Recuperación de emergencia por ingeniería social:** quien convenza a la plataforma de que es el admin de una empresa consigue que se ejecute `reinvitar-admin`. La defensa es el procedimiento fuera de banda (6.3), que el código no puede imponer. Si el procedimiento falla, el admin real se queda sin acceso en el acto y lo nota; el atacante solo tendría la cuenta si además recibe el token, que se entrega por otro canal al contacto del contrato. La auditoría lo muestra. Es el mismo residuo de cualquier recuperación asistida (NIST SP 800-63B-4, 4.2).
- **Aviso de recuperación sin correo:** el aviso que pide NIST (4.2.3) está dentro de la API (`invitacion_pendiente`, auditoría). El titular solo lo ve si consulta `/yo`, y los admins, si consultan la lista de cuentas; con un frontend sería un aviso en pantalla, y con correo, un mensaje. La recuperación de emergencia no depende de esto: revoca en el acto y el titular lo nota al intentar entrar.
- **Bloqueo residual del camino sin confianza:** quien conozca un email (el identificador de la empresa es público) puede fallar a propósito y mantener cerrado el login de esa cuenta **desde dispositivos nuevos**: esperas de hasta 60 minutos y, con 100 fallos, el camino queda cerrado hasta una reinvitación. Se acepta porque la alternativa es peor: sin bloqueo, la fuerza bruta no tiene freno; con bloqueo de la cuenta entera, esa misma persona dejaría sin acceso a quien investiga, también desde sus equipos. Si el titular no tiene a mano ninguno de sus dispositivos de confianza (por ejemplo, de viaje con un portátil nuevo), también queda bloqueado. **Cómo lo detecta el admin:** en la lista de cuentas, `en_espera` y `camino_sin_confianza_cerrado`; en el log de la API, `EVENTO espera_sin_confianza` y `EVENTO cierre_sin_confianza`, con empresa y cuenta. **Cómo se recupera el titular:** entra desde un dispositivo de confianza; si no tiene ninguno a mano, espera (como mucho 60 minutos) o pide a un admin que lo reinvite: al activar, el contador vuelve a cero y el camino se abre, aunque el atacante puede volver a empezar; si es el único admin, `reinvitar-admin` (6.3). Es el mismo residuo que documentan OWASP y Entra.
- **Fallos contados sin esperar al disco:** las dos reservas de intentos (la del login y la del cambio de contraseña) confirman con `synchronous_commit` desactivado (6.3). **Motivo:** que el tiempo de respuesta no revele si la cuenta existe. Con confirmación normal, una cuenta real escribe su contador y espera el fsync del WAL, y un email inexistente no escribe nada y no espera: unos 3 ms de diferencia, medidos. **Alcance:** solo las reservas. El acierto (la sesión, el contador a cero, el dispositivo y la fila de auditoría) va en otra transacción y se confirma en disco con normalidad. **Impacto:** si PostgreSQL se cae, se pueden perder los fallos contados en sus últimos 600 ms como mucho (tres veces `wal_writer_delay`), sin inconsistencia. Un atacante no provoca esa caída, y en ese tiempo solo caben unos pocos intentos: el limitador admite 10 logins cada 5 minutos por cliente, y el semáforo, dos hashes a la vez. **Por qué es la causa raíz y no un parche:** la fuga venía de la espera al disco y no de la escritura; quitar la espera para todos los caminos la elimina. La alternativa, escribir una fila señuelo en los caminos sin cuenta, igualaría el tiempo a costa de llenar la base de datos de filas falsas y de seguir dependiendo de que el disco tarde lo mismo en los dos caminos.
- **Sin lista de contraseñas filtradas:** NIST la recomienda, pero exige una lista actualizada y el contenedor no tiene internet. Con el TOTP obligatorio, una contraseña filtrada sola no basta.
- **Horas del lado del personal:** sesiones, dispositivos, invitaciones y esperas guardan marcas de tiempo, porque las necesitan para caducar. Son del personal, nunca del denunciante, y no tocan las tablas del camino anónimo.
- **Token de invitación por la salida de `gestion`:** sin correo, `alta-admin` y `reinvitar-admin` lo imprimen una vez para entregarlo. Caduca a las 72 horas y sirve una vez; si su titular lo encuentra usado, la auditoría de la empresa lo muestra.
- **Autoasignación de un admin:** un admin puede asignarse cualquier denuncia de su empresa y leerla, también una que le afecte. No se impide, porque alguien tiene que clasificar y la ley pone al Responsable del Sistema en ese papel; se hace visible: la fila de asignación con actor y destino el mismo, que cualquier otro admin ve por la API (6.7, 6.15). Con dos admins (6.3), uno ve lo que hace el otro.
- **Denuncias de una cuenta dada de baja:** siguen asignadas a ella hasta que un admin las reasigne; el listado las marca (`asignada_activa: false`), pero nada avisa de forma activa.
- **Lectura y mensajes del denunciante:** mientras el personal lee una denuncia, un mensaje del denunciante a esa misma denuncia espera a que termine la transacción (milisegundos; el descifrado va fuera).
- **Un JSON que no se puede analizar no consume el límite por cuenta:** FastAPI lo rechaza (422) antes de ejecutar las dependencias, así que no llega a autenticar (comprobado con la versión fijada). No toca la base de datos ni la sesión, y lo frena el límite por IP. Un cuerpo bien formado pero inválido sí autentica y sí cuenta.
- **Verificar la auditoría es O(n):** cada verificación recorre la cadena entera. Con muchos años de filas, agotaría el `statement_timeout` de 5 s y respondería 503. La solución de fondo es anclar el último hash fuera de la base de datos y verificar desde el ancla (diseñado, no implementado, 02_esquema.sql).
- **Fila de lectura aunque el descifrado falle:** la auditoría registra el acceso al confirmar la transacción y el descifrado va después; si fallara la integridad, quedaría una lectura sin contenido entregado. Se prefiere registrar el intento.
- **Frontend web:** diseñado, no implementado. Con navegador, los tokens irían en cookies `__Host-` (`HttpOnly`, `Secure`, `SameSite=Strict`) y habría que añadir defensa CSRF; solo cambiaría `app/rutas_personal.py` (6.3).
- **Vulnerabilidades sin arreglo publicado:** la imagen de la API (Debian 13.7, de `python:3.12-slim`) tiene 44 hallazgos HIGH sin arreglo (`util-linux`, `ncurses`, bibliotecas de `systemd`, `perl-base` con arreglo aplazado). Son paquetes esenciales de la base que no se pueden quitar; la batería no falla por ellos, pero los lista en cada ejecución. Una base distroless los reduciría, a costa de cambiar de versión de Python y de imagen, un cambio que no se hace sin probarlo entero.
- **Lo que Trivy no ve:** el OpenSSL y la libpq que traen dentro los wheels de `cryptography` y `psycopg-binary` (Trivy ve esos paquetes de Python y sus avisos, no las bibliotecas que llevan dentro; comprobado en el SBOM), y el propio CPython, que la imagen oficial compila desde el código fuente sin metadatos de paquete. Se cubren actualizando las versiones fijadas cuando sus proyectos publican arreglos.
- **El escaneo es una foto:** un resultado OK vale el día de la ejecución. Hay que programar la batería de forma periódica (6.17), igual que la supresión; sin eso, una vulnerabilidad publicada mañana pasaría desapercibida.
- **Caddy sin HTTP/2 mientras no haya imagen arreglada:** las tres declaraciones VEX caducan a los 30 días y obligan a revisar si ya hay una imagen de Caddy con Go 1.26.9 o posterior; con ella, vuelve `protocols h1 h2` y se retiran.
- **gitleaks sin firma:** sus imágenes no están firmadas. Lo que queda es el mismo digest en dos registros, la espera de 14 días y el digest fijado.
- **gitleaks no mira `secrets/` ni lo que no se podría commitear:** a propósito, para no abrir los secretos. Un fichero de `secrets/` solo llegaría al repositorio si alguien cambiara el `.gitignore`, y la batería comprueba que Git solo sigue `.gitkeep` y `README.md` ahí.
- **El hash se verifica sobre el wheel de esta plataforma:** pip comprueba que el fichero descargado coincide con alguno de los hashes de su paquete; los de otras plataformas no se descargan y no se comprueban.
- **`samenet` incluye el loopback:** además de la subred `data`, admite `127.0.0.1` (comprobado: `aplicacion` entra por loopback con la regla 2 de `pg_hba.conf`). Solo le sirve a quien ya está dentro del contenedor de PostgreSQL, y aun así necesita la contraseña del rol.
- **Renovación de los certificados internos de Caddy, sin probar por comportamiento:** la hoja dura 12 horas y Caddy la firma en local con su CA (`modules/caddytls/internalissuer.go` de Caddy v2.11.7, `defaultInternalCertLifetime`); la intermedia dura 7 días, y la CA la revisa cada 10 minutos y la renueva cuando le queda el 20 % de su vida (`modules/caddypki/ca.go`), con almacenamiento local. Está leído en el código, no comprobado: exigiría esperar horas. La parte de la biblioteca smallstep que firma no se ha leído entera.
- **Caddy ve el texto en claro y tiene salida a internet:** termina el TLS, así que ve cada petición descifrada, y la red `edge` le da salida (6.11). Un Caddy comprometido podría sacar lo que pasa por él. Dos alternativas, documentadas y no implementadas antes de la entrega:
  1. En un anfitrión Linux de producción, una regla en la cadena `DOCKER-USER` de iptables que corte las conexiones nuevas salientes desde `10.88.1.0/28`. Queda fuera del compose y depende del anfitrión.
  2. Un reenviador TCP en `edge` (sin TLS, así que sin texto en claro) y Caddy solo en redes internas, con PROXY protocol v2 para conservar la IP del cliente que usa el limitador (6.9). Es un cambio de arquitectura: una imagen nueva que fijar y escanear, y las pruebas de IP que rehacer.

## 9. Cumplimiento normativo

Contrastado con el texto consolidado de la Ley 2/2023 en el BOE (BOE-A-2023-4513):

- **Art. 9.2.c**, acuse de recibo "en el plazo de siete días naturales": la respuesta 201 con el código y la fecha es un acuse inmediato.
- **Art. 9.2.d**, plazo máximo de respuesta a las actuaciones de investigación (tres meses): el cierre exige un mensaje final que el denunciante lee en su seguimiento (6.15).
- **Art. 9.2.e**, "posibilidad de mantener la comunicación con el informante": el seguimiento por código, los mensajes del denunciante (6.13) y los del personal que tiene la denuncia asignada (6.15).
- **Art. 32.1**, acceso limitado al Responsable del Sistema y a quien lo gestione directamente, y **art. 8.5**, evitar el conflicto de interés: el contenido solo lo lee quien tiene la denuncia asignada, y cada lectura y asignación queda en la auditoría (6.15).
- **Art. 26**, libro-registro "de las informaciones recibidas", que "no será público": la tabla `denuncia`, con RLS por empresa. Art. 26.2: "En ningún caso podrán conservarse los datos por un período superior a diez años". Implementado en la supresión (6.14): a los diez años se suprime en cualquier estado.
- **Art. 32.4**, supresión de los datos "transcurridos tres meses desde la recepción de la comunicación sin que se hubiesen iniciado actuaciones de investigación", salvo para dejar evidencia del funcionamiento del sistema; las comunicaciones a las que no se ha dado curso solo pueden constar de forma anonimizada. Implementado (6.14): `canal.suprimir_denuncias_caducadas()`, único camino de borrado, con una fila de auditoría anonimizada por denuncia suprimida. Una comunicación a la que no se da curso pasa a `inadmitida`, que la supresión trata igual que `nueva` (6.15).
- **Art. 32.3**, "si se acreditara que la información facilitada o parte de ella no es veraz, deberá procederse a su inmediata supresión desde el momento en que se tenga constancia de dicha circunstancia", salvo que pueda constituir delito. Implementado (6.14 y 6.15): un admin declara la denuncia `no_veraz`, la API deja de mostrarla en el acto y la siguiente supresión la destruye. **Supresión real y no bloqueo:** el art. 32.4 excluye de forma expresa el bloqueo del art. 32 de la LOPDGDD ("sin que sea de aplicación la obligación de bloqueo"); el 32.3 no dice nada. Lo resuelve su origen: el inciso final del 32.3 viene de la enmienda núm. 30 (BOCG-14-A-123-3, 28 de noviembre de 2022, pág. 20), cuya justificación es que, "si se suprime inmediatamente, no se podría iniciar ninguna acción judicial". El legislador entendió la supresión como destrucción sin bloqueo, y la excepción penal es la que hace de bloqueo. También lo pide la minimización: un bloqueo guardaría años una información que se sabe falsa.

### Protección de datos (título VI de la Ley 2/2023)

Citas copiadas del texto consolidado del BOE. Unas obligaciones las cumple el sistema; otras son de la empresa que lo usa, como responsable del tratamiento, y aquí solo se señalan.

Lo que hace Canario:

- **Art. 29**, "No se recopilarán datos personales cuya pertinencia no resulte manifiesta para tratar una información específica o, si se recopilan por accidente, se eliminarán sin dilación indebida": la denuncia solo pide categoría y texto, y no se guardan IP ni hora (6.5 y 6.8). Lo recopilado por accidente se tacha con la redacción (6.18).
- **Art. 32.2**, los datos "que no sean necesarios para el conocimiento e investigación de las acciones u omisiones a las que se refiere el artículo 2" se suprimen de inmediato; "se suprimirán todos aquellos datos personales que se puedan haber comunicado y que se refieran a conductas que no estén incluidas en el ámbito de aplicación de la ley"; y "Si la información recibida contuviera datos personales incluidos dentro de las categorías especiales de datos, se procederá a su inmediata supresión, sin que se proceda al registro y tratamiento de los mismos". Implementado con la redacción (6.18), que tacha la parte y conserva el resto. Decidir qué es innecesario o de categoría especial es de quien instruye: el sistema no lo detecta. Si una comunicación entera queda fuera del ámbito de la ley, su texto se puede tachar entero y pasarla a `inadmitida`, que se suprime a los tres meses (6.14).
- **Art. 31.2**, "La persona a la que se refieran los hechos relatados no será en ningún caso informada de la identidad del informante": el sistema no la conoce (6.1).
- **Art. 32.1**, acceso limitado, también a "Los encargados del tratamiento que eventualmente se designen": quien opere la plataforma para varias empresas trata los datos por cuenta de cada una. Su acceso técnico y sus límites están en 6.12 y 8.
- **Arts. 32.3, 32.4 y 26.2**: arriba.

Lo que es de la empresa:

- **Base jurídica (art. 30):** "Se considerarán lícitos los tratamientos de datos personales necesarios para la aplicación de esta ley"; según el art. 30.2, por obligación legal (art. 6.1.c del RGPD) si el sistema es obligatorio y por interés público (art. 6.1.e) si no. Las categorías especiales, por "razones de un interés público esencial" (art. 30.5, art. 9.2.g del RGPD). El art. 30.5 da la base de licitud; la supresión inmediata de esos datos la impone el art. 32.2.
- **Informar (arts. 31.1 y 32.5):** a los informantes, de que su identidad es reservada, y a empleados y terceros, del tratamiento. Es un texto de la empresa; un frontend lo mostraría antes de enviar la denuncia.
- **Derechos (art. 31.3, arts. 15 a 22 del RGPD):** los atiende la empresa. El sistema no busca por persona: localizar los datos de alguien exige leer las denuncias. Si la persona a la que se refieren los hechos se opone, se presume, "salvo prueba en contrario", que existen "motivos legítimos imperiosos que legitiman el tratamiento de sus datos personales" (art. 31.4).
- **Si un dato de categoría especial que es el objeto de la denuncia** (por ejemplo, una discriminación por salud) **debe tacharse:** el art. 32.2 no hace excepciones y no se ha encontrado un criterio de la AEPD que lo aclare. Lo decide el Responsable del Sistema con su delegado de protección de datos.
- **Las obligaciones generales del responsable del tratamiento** (registro de actividades, evaluación de impacto si procede, delegado de protección de datos), que este documento no evalúa.
